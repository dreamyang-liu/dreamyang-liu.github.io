Dockerfile

A Dockerfile is a text file containing the definition of a container image, which can be used to launch containers. This definition includes commands, a base image, configuration, and more. In this post we’ll walk through each component and discuss when to use each one. Let’s get started.

Docker Images

Before diving into the individual components, you might want to know what a Docker image actually is. Reference: Structure of an Image

An image is a read-only template with instructions for creating a Docker container. Often, an image is based on another image, with some additional customization. –Docker Official Docs

Base Image / Parent Image

In most Dockerfiles, the first line you’ll see is FROM {base image}, for example FROM python:3.8.

This line defines the base image for the image we’re building. A base image may itself consist of one or more layers.

RUN

The RUN command can be used to execute commands such as installing packages, downloading files, and so on. One important thing to note is that each command adds a new layer on top of the existing image. Combining multiple commands into a single RUN instruction is a common trick to reduce image size and minimize the number of layers.

CMD

CMD describes the default parameters or command for the container. Users can easily override the default command at runtime.

ENTRYPOINT

ENTRYPOINT also defines a command that always runs, meaning it cannot be overridden. ENTRYPOINT can be used to ensure that a specific command is always executed when the container starts, even if the user tries to override it.

COPY

COPY can be used to copy local files into the container image, and nothing more.

Dive is a very useful tool for analyzing container images. It lets you see the commands for each layer and the corresponding changes reflected in the filesystem.

Docker Filesystem

Docker supports many configurable filesystems; the most commonly used and recommended one today is overlay2, which offers good performance and stability. If you list Docker’s DataRoot directory, you’ll find many subdirectories, one of which is overlay2 — that’s where overlay2 stores its data.

Inside you’ll find many subdirectories whose names are hash strings. These directories are the storage locations for the filesystems of individual images; each one is a layer, which could be a layer of an image, a layer of a currently running container, or a layer of a volume.

The hash in each folder name is not the layer’s sha256; it’s a short ID — the diff directory name assigned by Overlay2 on disk for that layer.

Key points of the Overlay2 storage structure:

  1. Image metadata & LayerDB
    • /var/lib/docker/image/overlay2/imagedb/content/sha256/<digest>
    • /var/lib/docker/image/overlay2/layerdb/sha256/<digest>/cache-id
      The content of this file (a short ID such as 36849485abab637c0…) is the diff directory name that Overlay2 assigned on disk for that layer.
  2. Overlay2 working directories
    • /var/lib/docker/overlay2/<cache-id>/diff
      Stores the actual file contents for that layer.
    • /var/lib/docker/overlay2/<cache-id>/merged
      The mount point when a container is running; on read, LowerDir + UpperDir are overlaid here.
