CUDA Graph: A Deep Dive

2026-06-03
cuda cuda-graph gpu pytorch mlsys

An interactive visualization guide to understanding GPU execution optimization. Every GPU kernel launch carries CPU overhead; CUDA Graph records an entire kernel sequence into a graph and replays it with a single launch. This post is written in Markdown, with interactive animations illustrating the key mechanisms.

1. The Problem: Death by a Thousand Kernel Launches

Every GPU kernel launch carries CPU overhead. For large kernels this is negligible, but modern deep learning runs hundreds of small kernels per step.

The animation below compares the CPU/GPU timeline with and without Graph. Without it, the CPU spends most of its time on driver overhead (red gaps) while the GPU idles waiting for the next launch instruction. With Graph, a single launch triggers the entire kernel sequence.

2. How CUDA Graph Works: Three Phases

CUDA Graph operates in three phases:

  1. Capture: All GPU operations are recorded into a graph structure. No actual computation happens during this phase.

  2. Instantiate: The graph is compiled into an executable form. Dependencies are validated and resources are allocated. This usually happens automatically when capture ends.

  3. Replay: The entire graph is executed via a single CPU launch. This is the fast path.

The captured graph records all operations and their dependencies as a DAG — for example: Input Buffer → {LayerNorm, Attention} → MatMul → GELU → Output Buffer.

3. Graph-Friendly vs. Non-Graph-Friendly Code

The basic rule: everything captured must be identical on every replay — same operations, same shapes, same memory addresses.

The interactive checker below lets you click each line of code to determine whether it is Graph-Friendly:

Operations That Break Graph Capture Graph-Friendly Patterns
Data-dependent control flow Fixed-shape tensor ops (matmul, conv)
Dynamic tensor shapes In-place buffer updates (.copy_())
Memory allocation / deallocation Static control flow (no runtime branches)
CPU-GPU sync (.item(), .cpu()) Pre-allocated memory pools
print on GPU tensors Fixed kernel grid dimensions
Variable-length loops cuDNN/cuBLAS with fixed parameters
cudaMalloc / cudaFree Pad to max shape + masking
cudaStreamSynchronize Condition checks performed outside the graph

4. Memory Model: Why Addresses Matter

During Capture the GPU memory layout is recorded:

During Replay the same addresses must be used — only the data can change. If a tensor gets reallocated to a new address (e.g., 0x7f02_0000 → new_alloc [8, 512]), the replay will fail.

Key rule: You can modify the data at a recorded address (via .copy_()), but you cannot change the address itself. This means: no reallocating memory, no changing shapes, no creating new tensors during replay.

6. When Does CUDA Graph Actually Help?

Scenario Without Graph With Graph Speedup
LLM Decode (small model) ~2.1ms/token ~0.7ms/token 3x
ResNet-50 inference ~4.2ms ~2.8ms 1.5x
Large matmul (4096×4096) ~12ms ~11.5ms 1.04x
Training step (many small kernels) ~8ms ~5ms 1.6x

Rules of thumb:

  • Many small kernels (each <100μs) → huge gains (2–5x)
  • Medium kernels (100μs – 1ms) → moderate gains (1.3–2x)
  • Few large kernels (each >10ms) → almost no gain (<1.1x)

8. Decision Flowchart: Should You Use CUDA Graph?

Answer each question in order; all must be “yes” to recommend it:

  1. Does the workload execute repeatedly with the same shapes? (No → skip)
  2. Are the kernels small (each <1ms)? (No → probably not worth it)
  3. Can all memory be pre-allocated? (No → refactor first)
  4. No data-dependent branches inside? (No → split into multiple segments)
  5. Will it be replayed many times (>100)? (No → skip)

All satisfied → Use CUDA Graph! Expect 1.5–5x speedup.

9. Common Pitfalls and Solutions

Pitfall: Forgetting to Warm Up Before Capture. CUDA lazily initializes its context, cuDNN algorithm selection, and JIT compilation. If you capture before warming up, these one-time operations get baked into the graph.

Pitfall: Forgetting .clone() When Using Graph Output. The output tensor is a fixed buffer; if you don’t clone it before the next replay, the data will be overwritten.

Pitfall: cuDNN Benchmark Mode. cuDNN benchmark mode selects different algorithms across runs; the graph may capture a suboptimal one.

Pitfall: Graph Pool Memory Fragmentation. Each graph captures its own memory pool; too many graphs leads to GPU memory fragmentation. Use a shared pool instead.

Pitfall: Gradient Accumulation Inside a Graph. If you graph a training step, gradients accumulate in the same buffer — be careful about where you zero gradients (inside or outside the graph).

10. Quick Reference Card

Pre-graph Checklist:

  • All tensor shapes are fixed
  • No .item() / .cpu() / print inside
  • No dynamic memory allocation inside
  • No data-dependent branches
  • Warmup iterations completed
  • cudnn.benchmark disabled or stabilized
  • Outputs cloned before next replay
  • Will replay >100 times
