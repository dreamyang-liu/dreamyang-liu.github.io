Hash Table

2026-06-02
Data Structures Hash Table

A hash table isn’t really a data structure at its core — it’s an algorithmic pattern: trading O(1) lookups for O(N) scans. Any time you see “find two elements satisfying some relation,” your instinct should reach for a hash table.

Intuition — O(1) Lookup in Place of O(N) Scan

Most brute-force problems look like this: enumerate all (i, j) pairs and check whether they satisfy some condition. O(N²).

What a hash table does is extremely simple: as you iterate, throw each “already-seen” element into the table; for every new element, ask the table whether there’s anything inside that can pair with it. One pass + O(1) lookup per step = O(N).

Boiled down to one sentence:

Turn an O(N²) “pair enumeration” into an O(N) “look up as you go.”

When it applies:

  • The problem asks for two elements satisfying f(a, b) = target (two-sum, 4Sum II, find pair with given difference/sum/product)
  • The problem asks “did X appear before?” (longest substring without repeating characters, contains duplicate)
  • The problem asks you to count “how many times does a certain value appear?” (counting, group anagrams)
  • The problem wants to compress an O(N) range query into O(1) (prefix sum + hash, covered below)

set vs. dict: use a set when you only care about whether something has been seen; use a dict when you need to store extra information (index, count, last-seen position). Two-sum needs to return indices, so it’s a dict; duplicate detection is a set. Don’t default to dict just to look fancy.

Animation: “Look First, Then Store” for Two Sum

Array [2, 7, 11, 15], target = 9. Pay attention to two things:

  1. For each new element x, query the table for target - x first, and only insert x afterward.
  2. The seen dict grows from empty; when the 2nd element 7 arrives, 2 is already in the table — immediate hit.

Templates — Two Sum, Subarray Sum Equals K

Pattern 1: Two Sum (look first, then store)

Why must you always look first, then store? Consider nums = [3, 3], target = 6: if you store first, the first 3 goes in and immediately matches itself, returning [0, 0] — the same element paired with itself. Looking first keeps the current element out of the table.

Prefix Sum + Hash Combination

This is the hash trick that creates the biggest skill gap in algorithm problems. Subarray sum = prefix[j] - prefix[i], so “subarray sum equals k” is equivalent to “find two prefix sums whose difference is k” — which is just two-sum again.

Two critical points:

  • {0: 1} must not be omitted: it represents the “take nothing” empty prefix. Without it, any valid subarray starting at index 0 will be missed.
  • “Look first, then store” still applies: use the old prefix counts to update count first, then write the current curr_sum into the table. Otherwise the current position will count itself as a “previous segment.”

Once you internalize this combination, the following problems all collapse into the same one:

Variant What to store as key
Sum equals k prefix_sum
Sum divisible by k prefix_sum % k
Binary tree path sum (437) maintain prefix along the path
Equal number of 0s and 1s in subarray treat 0 as -1, then find sum = 0

Mnemonics / Common Pitfalls

  • See “pairing” → think hash: whenever the problem says “two numbers satisfying…”, “does there exist…”, “did it appear before…” — reflexively reach for a hash table.
  • Look first, then store: never let the current element pair with itself.
  • set vs. dict: only asking “seen?” → set; need to store index/count/position → dict.
  • Prefix-sum hash must be initialized with {0: 1}: covers subarrays that start from index 0.
  • Be careful modifying a dict during iteration: key changes can affect subsequent logic; copy or defer writes when necessary.
  • Worried about collisions on large data: custom objects used as keys must implement both __hash__ and __eq__, and the two must be consistent.
  • Only immutable objects can be keys: list no, tuple yes; set no, frozenset yes.

Exercises

Why must two-sum use "look first, then store"? Give an example where "store first, then look" produces a wrong answer.

nums = [3, 3], target = 6. Store first: the first 3 is written as seen[3]=0, then immediately queried as 6-3=3 — found in the table, returns [0, 0] — the same element paired with itself. Wrong.

Look first: when the first 3 arrives the table is empty, query misses, then it’s stored; when the second 3 arrives it finds the first 3 in the table and returns [0, 1]. Correct.

In prefix sum + hash, what does {0: 1} initialization represent? What gets missed without it?

It represents “the empty prefix that takes nothing, has sum 0, and has appeared once.”

When some curr_sum exactly equals k (i.e., the subarray from index 0 up to the current position sums to k), the code looks up prefix[curr_sum - k] = prefix[0]. Without initialization, all such “starts-from-zero” subarrays are missed.

Example: nums = [1, 2, 3], k = 3; the subarray [1, 2] is counted precisely because prefix[0]=1 is there.

Why does Counter subtraction c1 - c2 keep only positive results? When is this useful?

Counter is a multiset — element counts can’t go negative. Subtraction means “remove,” and removing more than you have clips to zero.

Use cases:

  • Check if word can be spelled from available letters: if Counter(word) - Counter(available) is empty, yes it can.
  • Find missing letters: Counter(required) - Counter(have).
  • Sliding-window character frequency comparison.
