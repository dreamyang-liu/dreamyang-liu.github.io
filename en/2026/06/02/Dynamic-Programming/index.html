Dynamic Programming

DP = subproblems + no redundant computation. It compresses exponential search into polynomial time — all by “never recomputing what you’ve already computed.”

Intuition — Non-overlapping Subproblems

DP really boils down to two steps. Memorize them:

  1. State definition: dp[i][j] represents some property of “the first i / first j” elements (length, count, feasibility, optimal value). Get the state right and the problem is halfway solved.
  2. Transition equation: how to build the current dp[i][j] from smaller subproblems.

Two hallmarks of a DP problem:

  • Optimal substructure: the optimal solution to the large problem is built from optimal solutions to smaller subproblems.
  • No aftereffect: once the current state is determined, how you got there has no bearing on future decisions.

Two equivalent implementations — pick whichever feels natural:

  • Memoized recursion (top-down): looks like brute-force search; slap @cache on it and it becomes DP. No need to reason about traversal order; only computes visited subproblems.
  • Iterative table-filling (bottom-up): compute small before large; loop order mirrors dependency order. No recursion stack, easier to optimize space.

Three Paradigms

Master three archetypal problems and 90% of DP questions are just variations of them.

Linear DP — Climbing Stairs Style

State depends on only a fixed number of earlier positions. A one-dimensional array suffices.

Same pattern: House Robber (dp[i] = max(dp[i-1], dp[i-2]+nums[i])), Maximum Subarray, Minimum Path Sum.

LIS — Picking a Subsequence

dp[i] = length of the longest increasing subsequence ending at nums[i]. Note it’s “ending at i,” not “among the first i” — otherwise you can’t write the transition.

There is also an greedy + binary search solution (maintain a monotone tails array, binary-search insert). Know both for interviews.

Knapsack — Multi-stage Decision Making

“Include or not / include how many times” for each item — the highest-frequency DP paradigm.

LCS / Edit Distance also fall here (“current characters match or not” is a two-way decision):

0/1 Knapsack: each item used at most once. 1-D optimization → reverse capacity order.

Unbounded Knapsack: each item used any number of times. 1-D optimization → forward capacity order.

Knapsack variant cheat sheet (the animation shows the difference between the two orderings):

Problem Initialization Transition
Max value dp = [0]*(W+1) dp[j] = max(dp[j], dp[j-w]+v)
Count solutions dp[0]=1, rest 0 dp[j] += dp[j-w]
Feasibility dp[0]=True dp[j] = dp[j] or dp[j-w]
Combinations vs permutations — items outer loop = combinations; capacity outer loop = permutations

2-D → one row (knapsack pattern, traversal order preserves semantics):

  • 0/1 knapsack: j reverse order — dp[j-w] still holds the previous round’s value (“item i not yet selected”).
  • Unbounded knapsack: j forward order — dp[j-w] already reflects the current round’s update (“item i can be selected repeatedly”).

Get the order wrong and items are either selected multiple times or not at all. This is the most common knapsack bug.

Mnemonics / Common Pitfalls

Three rules of thumb:

  • Define the state first, then write the transition.
  • Cover all base cases; get the traversal order right.
  • Roll to one row: 0/1 goes reverse, unbounded goes forward.

Common mistakes:

  • Off-by-one: state dp[i] means “first i elements” → index into the array as s[i-1], not s[i].
  • Missing base cases: when counting solutions, dp[0]=1 (the empty set counts as one); when optimizing, initialize in the direction consistent with max/min.
  • Wrong LIS state: must be “ending at i,” not “among first i” — otherwise the transition cannot be written.
  • Knapsack order: reverse/forward order and which of items/capacity is the outer loop are two independent dimensions — don’t conflate them.
  • Stale cache: @cache leaks data across multiple test cases; call cache_clear() before returning from the function.

Exercises

Q1: Why does 0/1 knapsack require reverse capacity order? What goes wrong with forward order?

With forward order, dp[j-w[i]] may already have been updated in the current round, which means item i is used more than once — that is the unbounded knapsack. Reverse order ensures dp[j-w[i]] still holds the previous round’s value (item i not yet selected).

Q2: When should you choose memoized recursion vs iterative DP?

Afraid of getting it wrong → memoized recursion (no need to think about order; only computes needed subproblems). Need to save space / large input → iterative table-filling (no stack risk; rolling array is straightforward). Python’s default recursion limit is 1000; for deep state spaces, remember sys.setrecursionlimit.

Q3: Why do "combinations" and "permutations" in knapsack require different traversal orders?

Items as outer loop: each item is considered in a fixed order, so (1,2) and (2,1) count as one = combinations. Capacity as outer loop: every capacity scans all items, so the same set of items can appear in different orders = permutations.
