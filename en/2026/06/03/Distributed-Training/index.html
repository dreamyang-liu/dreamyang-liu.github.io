Distributed Training and Communication Primitives

2026-06-03
distributed-training parallelism mlsys nccl fsdp ring-allreduce

As model scale grows exponentially, a single GPU can no longer hold an entire model. This post systematically covers data/tensor/pipeline/sequence/expert parallelism, NCCL collective communication primitives, Ring AllReduce, FSDP/ZeRO, and communication–computation overlap — the core mechanisms of distributed training. The body is markdown, with interactive animations for key mechanisms (step through with buttons).

3.0 Why Do We Need Distributed Training?

As model scale grows exponentially (GPT-3: 175B, PaLM: 540B, Llama 3: 405B), a single GPU can no longer hold an entire model’s parameters, gradients, and optimizer states. Distributed training spreads computation and storage across multiple devices, making it possible to train truly massive models.

Core challenge: Minimize communication overhead and maximize GPU utilization while preserving mathematical training equivalence.

Three fundamental parallelism strategies can be combined (called 3D Parallelism):

Strategy What Gets Split Communication Pattern When to Use
Data Parallelism (DP) Data (batch) AllReduce gradients Model fits on a single GPU
Tensor Parallelism (TP) Per-layer parameters AllReduce / AllGather A single layer is too large
Pipeline Parallelism (PP) Layer-wise split Point-to-point Send/Recv Model has many layers

3.1 Parallelism Strategy Comparison

Data Parallelism

Core idea: Each GPU holds a complete replica of the model. A mini-batch is evenly divided into micro-batches; each GPU independently runs forward and backward passes, then gradients are synchronized via AllReduce.

A Mini-Batch (B=32) is distributed to 4 GPUs, each holding a complete model replica. After independent computation, gradients are synchronized through AllReduce — after synchronization all GPUs hold identical gradients, and parameters stay consistent after the update.

Advantages and limitations

  • Simple to implement; PyTorch’s DistributedDataParallel works out of the box
  • Communication volume: each iteration requires AllReducing all gradients (2M bytes, where M = parameter count)
  • Limitation: model must fit in a single GPU’s memory
  • Limitation: communication overhead grows linearly with GPU count (though Ring AllReduce mitigates this)

Pipeline Parallelism

Core idea: Split the model into stages by layer, placing each stage on a different GPU. Data flows between stages as micro-batches. For example: Stage 0 (Layers 0–5) on GPU 0, Stage 1 (Layers 6–11) on GPU 1, and so on.

Common scheduling strategies

  • GPipe: Complete all forward micro-batches first, then all backward passes
  • 1F1B: Interleave forward and backward passes to reduce peak memory
  • Interleaved 1F1B: Each GPU holds multiple non-contiguous stages, further reducing bubbles

3D Parallelism (Hybrid Parallelism)

When training truly large models in practice, DP + TP + PP are typically used simultaneously. For example, Megatron-Turing NLG (530B) uses (2048 GPUs):

Dimension Degree Notes
Tensor Parallelism 8 8 GPUs within a single node (NVLink high bandwidth)
Pipeline Parallelism 8 Cross-node; small communication volume (only activations)
Data Parallelism 32 2048 / (8×8) = 32-way data parallelism
Total GPUs — 8 × 8 × 32 = 2048

Design principles

  • TP stays intra-node: leverages NVLink/NVSwitch high bandwidth (900 GB/s on H100)
  • PP crosses nodes: point-to-point communication volume is small, lower bandwidth requirement
  • DP scales across the remaining dimension: use gradient accumulation to further hide communication

Sequence Parallelism

When sequence lengths are long (e.g., 128K+ tokens), even the activations for a single layer can blow up memory. Sequence parallelism shards the sequence dimension across multiple GPUs.

The animation below shows the switch between TP regions and SP regions (4 GPUs):

Core idea: shard along the sequence dimension in non-TP regions. Tensor Parallelism already shards Attention and FFN across cards. But operations like LayerNorm and Dropout still keep the full-sequence activation on every card — which is redundant.

  • TP region (already sharded): QKV Proj → Attention → O Proj → FFN
  • SP region (sequence-sharded): LayerNorm, Dropout, Residual Add
  • TP-to-SP transition: AllReduce → ReduceScatter (forward) / AllGather (backward)
Benefit Notes
Memory savings Activation memory reduced to 1/TP_size (e.g., TP=8 → 87.5% activation savings)
Communication overhead No extra communication! The existing AllReduce is split into ReduceScatter + AllGather

Three region types, three sharding dimensions — understood in one row

Region Sharding dim Per-GPU shape Who shards it
SP region (LN i/o, residual) along seq (b, s/T, h) SP
TP region, attention (Q, K, V, scores, softmax, ctx) along heads (b, n_h/T, s, d_k) etc. TP
TP region, MLP (up, GeLU) along hidden (b, s, 4h/T) TP
Boundary transients (x1, x2 at TP region entry; attn_out, down at TP region exit) Full (b, s, h), but partial sum, immediately reduced by communication — (none, intermediate state)

Boundary transients look like they save nothing — but they are ephemeral states that computation flows through, immediately consumed by reduce-scatter or @ matmul as soon as they’re computed, and never live in memory simultaneously. In the peak memory accounting they count as one copy, not all transients at once.

Why ~8× savings

  • SP region (LN i/o, residual): largest contributor (6+ copies of (b,s,h) per layer), sharded along seq → 1/T
  • TP region attention: O(s²) term sharded by heads → 1/T
  • TP region MLP: 4× fat tensors (up + GeLU) sharded along hidden → 1/T
  • Boundary transients: not sharded, but only alive momentarily, counted as one copy in peak

Full formula (Korthikanti et al. 2022): activation per layer goes from 34·s·b·h + 5·a·s²·b → (34·s·b·h + 5·a·s²·b) / T, a full 1/T saving. Paired with selective recomputation to cut ~80% of O(s²) → in 70B training, per-GPU per-layer activation drops from 1.85 GB to ~50 MB.

For a detailed dissection of activation shapes at each position in the Transformer (x_in/Q/K/V/scores/MLP up and the three orders of magnitude, which tier FlashAttention eliminates, why output logits are 524 MB), see LLM Inference §4.1 “Where Activations Actually Live in the Transformer”.

Expert Parallelism

In Mixture of Experts (MoE) models, different experts are distributed across different GPUs. Each token is routed to top-k experts by a router.

Advantages Challenges
Parameter count can scale 10×, compute only ~2× (each token activates only top-k experts) All-to-All communication: each token must be sent to the GPU holding its target expert
Each GPU only stores a subset of expert parameters Load imbalance: popular experts may receive too many tokens (requires a load balancing loss)
Orthogonally composable with DP/TP/PP Token dropping: tokens are dropped when an expert’s buffer is full

3.2 NCCL Collective Communication Primitives

NVIDIA Collective Communications Library (NCCL) provides the low-level communication operations needed for distributed training. Understanding these primitives is foundational.

Operation Description Input → Output Comm volume (N GPUs, M bytes)
Broadcast Send one GPU’s data to all GPUs 1 copy → N identical copies
Reduce Reduce data from all GPUs to one GPU N copies → 1 aggregated copy
AllReduce Reduce data from all GPUs; result goes to all GPUs N copies → N identical aggregated copies
AllGather Gather data from all GPUs to all GPUs
ReduceScatter Reduce, then scatter shards to each GPU

Key insight: AllReduce = ReduceScatter + AllGather. This decomposition is the heart of the Ring AllReduce algorithm.

3.3 Ring AllReduce Algorithm Deep Dive

Ring AllReduce is one of the most classic AllReduce implementations, introduced into deep learning training by Baidu in 2017. Its core advantage is that communication volume is independent of GPU count (per-GPU bandwidth utilization stays constant).

Algorithm steps — Ring AllReduce has two phases, each with N-1 steps (N = number of GPUs):

  • Phase 1: Reduce-Scatter — after N-1 steps, each GPU holds 1/N of the final result
  • Phase 2: AllGather — after another N-1 steps, each GPU holds the complete final result

3.6 Communication Strategy Overhead Comparison

Communication patterns and overhead differ dramatically across parallelism strategies. The table below compares per-iteration communication volume under different configurations:

Strategy Primitive Per-GPU comm volume per iteration Frequency
DDP AllReduce Every backward step
FSDP (ZeRO-3) AllGather + ReduceScatter Every layer forward + backward
Tensor Parallel AllReduce per layer Every layer forward + backward
Pipeline Parallel P2P Send/Recv Every micro-batch

Trade-off: FSDP Stage 3 has 50% more communication volume than DDP, but the memory savings let you train models N times larger or use much bigger batch sizes.

What Is a CUDA Stream?

A CUDA Stream is an ordered command queue on the GPU. Think of it as a conveyor belt:

  • Operations within the same stream execute strictly in order (FIFO)
  • Operations across different streams can run in parallel — the GPU hardware schedules them automatically
  • By default, all operations go to stream 0 (the default stream), making everything serial

Single stream (serial): total time = A + copy + B. Multiple streams (parallel): total time = max(A+B, copy).

Key hardware basis: The GPU has independent hardware engines: SMs (Streaming Multiprocessors) for compute, Copy Engines (CE) for data movement, NVLink/PCIe DMA for cross-GPU communication. Multi-stream parallelism works because these engines are physically independent — it’s real hardware parallelism, not software-simulated concurrency.

Communication–Computation Overlap

The performance bottleneck in distributed training is often not communication itself but communication blocking computation. The core idea: keep the GPU doing useful work while waiting for data transfer, effectively “hiding” communication latency.

Why can they overlap? With the concept of multiple CUDA streams, the answer is natural: put communication and computation on different streams and the hardware runs them in parallel.

  • No overlap (naive): communication and computation are serial, Total = T_compute + T_comm
  • With overlap: communication and computation run in parallel, Total = max(T_compute, T_comm)

Technique 1: Gradient Bucketing (DDP)

DDP doesn’t fire off a communication for every individual gradient; instead it packs multiple gradients into a “bucket” (default 25 MB), starting from the last layer:

  1. Backward computes gradient for Layer N → placed into Bucket 1
  2. Bucket 1 is full → triggers async AllReduce (on the communication stream)
  3. Meanwhile, the compute stream keeps computing gradients for Layers N-1, N-2, …
  4. By the time all backward passes are done, the earlier AllReduces have long since completed

Technique 2: FSDP Prefetching

FSDP AllGathers the next layer’s parameters while computing the current layer. Both forward and backward passes use prefetching. During the forward pass, a layer’s parameters are freed immediately after computation to save memory. During the backward pass, three streams work simultaneously: compute current layer’s gradients | prefetch next layer’s parameters | send previous layer’s gradients (async ReduceScatter).

Technique 3: Async Communication (manual control)

The low-level API allows manually implementing overlap:

GPU hardware perspective: why overlap works

  • Compute stream: kernels execute on SMs, consuming CUDA Cores / Tensor Cores
  • Comm stream: NCCL moves data via the Copy Engine, not occupying SMs — completely independent hardware
  • Key insight: both sets of hardware can run at full capacity simultaneously; software just needs to place them on different CUDA streams

When does overlap break down?

  • Communication far exceeds compute: small models + many GPUs → AllReduce time >> single-layer backward time; can’t fully hide it
  • Insufficient bandwidth: multi-node setups connected by PCIe; the communication bottleneck is too large
  • Bubble phases: the warmup/cooldown phases of Pipeline Parallelism have no computation to overlap with
  • Single-stream implementation: if communication and computation are on the same CUDA stream, hardware cannot parallelize them

Overlap effectiveness comparison across three scenarios: ideal case (communication fully hidden, effective time = ); partial overlap (after compute finishes, still waiting for communication to complete, producing an idle bubble); no overlap (same stream or synchronous communication, Total = T_compute + T_comm).

Rule of thumb: When communication time / compute time ≤ 1, overlap can almost completely hide communication overhead. During real-world tuning, use torch.profiler‘s trace view to verify that the two streams are truly running in parallel.

3.7 Exercises

Exercise 1: Compute Ring AllReduce Communication Volume

Suppose you have N GPUs, each with gradients of size M bytes. Derive the total bytes sent and received per GPU in the Ring AllReduce algorithm. Specific question: When N=8 and M=2 GB (FP32 gradients for a 500M-parameter model), how much data does each GPU send and receive?

Complete solution:

  1. Data is split into N chunks, each of size M/N
  2. Reduce-Scatter phase: N-1 steps, each step sends M/N bytes
  3. AllGather phase: N-1 steps, each step sends M/N bytes
  4. Total sent = 2(N-1) × M/N = 2M(N-1)/N
  5. Total received is identical = 2M(N-1)/N

Plugging in N=8, M=2 GB: per-GPU communication = 2 × 2 GB × 7/8 = 3.5 GB. Note: compared to naive AllReduce (send to a root then broadcast) of 2M(N-1) = 14 GB, the ring approach dramatically reduces per-GPU bandwidth requirements.

Exercise 2: Design a Parallelism Strategy

You need to train a 70B-parameter model on 64 A100 80GB GPUs (8 nodes, 8 GPUs per node, NVLink interconnect). Given: training memory requirement (including optimizer) ~16 bytes/param = 1120 GB; NVLink bandwidth 600 GB/s (intra-node); InfiniBand bandwidth 50 GB/s (inter-node). Question: Design the DP/TP/PP combination and justify your choices.

Recommended setup: TP=8, PP=2, DP=4 (verify: 8 × 2 × 4 = 64 GPUs)

  1. TP=8 (intra-node): 70B / 8 TP = ~8.75B parameters stored per GPU; including activations ~35 GB, fits in 80 GB. TP communication is frequent (two AllReduces per layer), so NVLink high bandwidth is essential.
  2. PP=2 (cross-node): Split model into 2 stages, each ~35B parameters. PP only transmits activations (relatively small), suitable for InfiniBand bandwidth. Use enough micro-batches to reduce bubble ratio.
  3. DP=4: 64 / (8 × 2) = 4-way data parallelism. Can pair with ZeRO Stage 1 to further reduce optimizer state memory. Gradient AllReduce can be overlapped with backward computation.

Alternative: Using FSDP Stage 3 instead of TP+DP → PP=8, FSDP=8, but with higher communication overhead.

3.8 Chapter Summary

Concept Key Points
Data Parallelism Replicate model, split data, AllReduce gradients; simple but has memory bottleneck
Tensor Parallelism Split intra-layer weights (column/row split); requires high-bandwidth interconnect
Pipeline Parallelism Split model by layers; bubble ratio = (p-1)/(p-1+m)
Ring AllReduce Comm volume O(M), independent of GPU count; bandwidth-optimal
FSDP / ZeRO Shard optimizer states/gradients/parameters; Stage 3 gives linear memory reduction
3D Parallelism TP (intra-node) + PP (cross-node) + DP (scale-out); standard paradigm for training very large models
