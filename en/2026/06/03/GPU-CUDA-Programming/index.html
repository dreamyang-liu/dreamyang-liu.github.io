2.1 GPU Architecture: SMs, Warps, and the Thread Hierarchy

The Core Idea Behind GPU Parallelism

The fundamental difference between GPUs and CPUs lies in their design philosophy: CPUs optimize for low latency (a small number of powerful cores + large caches + complex control logic), while GPUs optimize for high throughput (thousands of simple cores + massive concurrency to hide latency).

  • Streaming Multiprocessor (SM): The basic compute unit of a GPU. Each SM contains multiple CUDA Cores, Tensor Cores, Load/Store units, and Shared Memory.
  • Warp: 32 threads form one warp — the smallest scheduling unit on the GPU. All threads in a warp execute the same instruction (SIMT).
  • Thread Hierarchy: Thread → Warp → Thread Block → Grid, forming a multi-level parallel structure.

Where Tensor Cores Fit in the Thread Hierarchy

Tensor Cores are warp-level compute units. Each MMA (Matrix Multiply-Accumulate) operation is completed cooperatively by an entire warp (32 threads):

Key properties of Tensor Cores:

  • Warp cooperation: Each of the 32 threads holds a different fragment of the A/B/C matrices. A single mma.sync instruction is executed cooperatively by the whole warp.
  • Data distribution: A/B fragments live in the registers of the 32 threads — they do not pass through Shared Memory.
  • Mixed precision: FP16/BF16/FP8 inputs, FP32 accumulator — balancing speed and numerical precision.
  • Throughput (H100): Each SM has 4 Tensor Cores, each capable of one MMA per cycle → single-SM peak ~200 TFLOPS (FP8).

Key Design Principles

  • Data reuse: Keep data in Shared Memory as long as possible to reduce HBM traffic.
  • Coalesced access: Threads in the same warp should access consecutive memory addresses so their requests can be merged into a single transaction.
  • Avoiding bank conflicts: Shared Memory is divided into 32 banks; avoid having multiple threads in the same warp access the same bank.
  • Occupancy tuning: Balance Shared Memory and register usage to maximize the number of active warps per SM.

2.3 GEMM and Tensor Cores

Why Is GEMM So Important?

The core operations in deep learning — fully-connected layers, convolutions, and the and products in attention — are all fundamentally matrix multiplications (General Matrix Multiply, GEMM). Optimizing GEMM means optimizing the entire training and inference pipeline.

A computation C[M,N] = A[M,K] × B[K,N] requires FLOPs (counting multiply and add separately). For the matrix sizes typical in LLMs (e.g., 4096×4096), this means billions of operations.

2.4 CUDA Graphs: Eliminating Kernel Launch Overhead

The Problem: Kernel Launch Overhead

Every time the CPU submits a kernel to the GPU, there is roughly 5–10 microseconds of launch overhead. For a single large kernel this is negligible, but in the decode phase of LLM inference dozens to hundreds of small kernels execute sequentially:

  • A single Transformer layer may involve 20+ kernels (LayerNorm, QKV projection, Attention, FFN, …).
  • If each kernel’s compute time is only 10–20 µs, launch overhead can account for 30–50% of total time.
  • The CPU becomes the bottleneck — the GPU sits idle waiting for the next kernel to be dispatched.

CUDA Graph Timeline Comparison (animation)

The CUDA Graph Three-Step Flow: Capture → Instantiate → Replay

CUDA Graph Limitations

  • Static shapes: Tensor shapes at capture time are fixed — dynamic shapes are not allowed.
  • No CPU dependencies: The graph cannot contain if/else branches, Python control flow, or CPU synchronization.
  • Fixed memory addresses: Input/output addresses are fixed at capture; only in-place writes are permitted afterward.
  • No dynamic allocation: torch.empty() and similar calls cannot appear inside a graph.
  • Best use case: the decode phase (inference loops with fixed batch size and sequence length).

2.5 Memory Management and Profiling

PyTorch CUDA Memory Allocator

PyTorch uses its own caching memory allocator to avoid frequent calls to cudaMalloc/cudaFree (each call requires a full GPU synchronization, which is very slow).

  • Block pool: Freed memory is returned to a pool rather than given back to CUDA, ready for reuse.
  • Fragmentation: After long training runs, the pool fills with small fragments that cannot be coalesced into large contiguous blocks.
  • Expandable segments (PyTorch 2.0+): Uses cudaMallocAsync or the virtual memory API to grow allocations on demand rather than all at once.

Memory Profiling in Practice

Enabling Expandable Segments

Common OOM Debugging Checklist

  • Check memory_reserved vs memory_allocated — a large gap indicates severe fragmentation.
  • Call torch.cuda.empty_cache() to release cached memory (note: does not affect tensors still in use).
  • Enable expandable_segments to reduce external fragmentation.
  • Use gradient_checkpointing to trade compute for memory.
  • Check for tensors being accidentally kept alive (a common culprit is a list accumulating loss values).

Kernel Launch and Occupancy

Choosing the right block size is critical for performance:

  • Block too small (e.g., 32 threads): cannot fully utilize SM resources; occupancy is low.
  • Block too large (e.g., 1024 threads): each block demands more resources, so fewer blocks fit on an SM.
  • Rule of thumb: 128 or 256 threads/block is usually a good starting point.
  • Use torch.cuda.get_device_properties() to query hardware parameters and guide your configuration.

Question: Classify each kernel as compute-bound or memory-bound, and walk through the Roofline Model analysis.

Solution:

Conclusion:

  • Kernel A (Vector Add) is memory-bound: optimize by reducing memory traffic, leveraging caches, and kernel fusion.
  • Kernel B (GEMM) is compute-bound: optimize by using Tensor Cores, improving occupancy, and tuning instruction scheduling.

This is exactly why operator fusion matters so much in LLM inference — fusing multiple memory-bound micro-kernels (e.g., bias add + activation + dropout) into one eliminates the intermediate HBM round-trips.

Exercise 3: CUDA Graph Applicability (true/false with explanation)

For each scenario below, decide whether CUDA Graph can be used and explain why:

  1. Scenario A: LLM decode phase, batch_size=8, seq_len grows by 1 each step (KV cache grows), but using paged attention.
  2. Scenario B: Fixed-batch-size image classification inference (ResNet-50), input always 224×224.
  3. Scenario C: Training forward pass, model contains if x.sum() > 0: path_a() else: path_b() — a data-dependent branch.
  4. Scenario D: vLLM prefill phase, different requests have different prompt lengths.

Solution:

  • Scenario A: Yes, with some care ✓. Paged attention kernel parameters (page table) can be passed via a fixed buffer. In practice, SGLang/vLLM use CUDA Graphs for decode: pre-compile graphs for a set of batch sizes (e.g., bs=1,2,4,8,16,…) and pad to the nearest size. The growing seq_len doesn’t affect the per-step decode computation (each step processes only 1 token).
  • Scenario B: Ideal use case ✓. Fixed input shapes, fixed model structure, no dynamic control flow — a textbook CUDA Graph application with significant speedup.
  • Scenario C: No ✗. if x.sum() > 0 is data-dependent control flow. At capture time, only the branch actually taken gets recorded. If a different branch is taken during replay, the graph still executes the recorded path, producing wrong results.
  • Scenario D: Not directly, but padding works ✓/✗. Prefill has variable seq_len across requests, so shapes are dynamic. Direct CUDA Graph use is not possible. However, like decode, you can pre-compile graphs for common seq_len buckets and pad shorter sequences. The trade-off: padding wastes compute, but saves launch overhead. For prefill, kernels are typically large enough that launch overhead is a small fraction — so the benefit is much less pronounced than in decode.

Solution:

Trade-off analysis (BLOCK_K=32 vs BLOCK_K=64):

Metric BLOCK_K=32 BLOCK_K=64
Shared Mem / block 32 KB 64 KB
Blocks / SM 7 3
Warps / SM 7×8=56 3×8=24
Occupancy 56/64 = 87.5% 24/64 = 37.5%
K-loop iterations K/32 K/64 (halved)
Compute per iteration 128×128×32 FLOPs 128×128×64 FLOPs (doubled)

Why does occupancy matter? — The SM warp scheduling mechanism

Key point: at any given moment, multiple warps are “in flight” on the same SM — not just one! The H100 has 4 warp schedulers per SM, each capable of issuing one instruction to one warp per cycle. So up to 4 warps execute simultaneously every cycle.

Warp state Meaning Count
Resident warps Resources (registers/smem) allocated; eligible to be selected any time up to 64/SM
Eligible warps Not waiting for data or a barrier; can be issued next cycle varies dynamically
Issuing warps Currently being dispatched by a scheduler up to 4/SM

Of the 64 resident warps, 4 are selected each cycle. The rest are either waiting for HBM data (~400 cycles), waiting at __syncthreads(), or eligible but not yet picked.

Key contrast with CPUs: Warp switching is zero overhead! Every resident warp’s registers remain in the Register File at all times (no save/restore needed). The scheduler simply advances its pointer to another warp’s PC — this is why GPUs can hide latency with many warps, while CPU context switches are expensive.

Higher occupancy → more resident warps → even if many warps are stalled waiting for memory, the scheduler can still find eligible warps to keep the pipeline full. Lower occupancy → all warps may be waiting on data → all 4 schedulers sit idle → GPU utilization collapses.

But higher occupancy is not always better:

  • BLOCK_K=64 advantage: half the loop iterations → fewer __syncthreads() calls, less loop branch overhead, more MMA instructions per iteration (amortizes the fixed costs of the instruction pipeline).
  • BLOCK_K=64 disadvantage: occupancy drops to 37% → if the kernel is latency-bound (interleaved compute and memory access without sufficient density), there aren’t enough warps to cover stall cycles.
  • When is larger BLOCK_K better? When the kernel is compute-bound (Tensor Core utilization is already high and each warp produces enough MMA instructions to keep the pipeline fed); in that case occupancy is not the bottleneck, and reducing loop overhead pays off more.
  • When is smaller BLOCK_K better? When K is small (few loop iterations to begin with) or the kernel has heavy non-compute work (e.g., epilogue stores and activation functions); then higher occupancy matters more.

Practical guidance: In Triton/CUTLASS, BLOCK_K is typically auto-tuned across {32, 64, 128}. cuBLAS uses similar heuristics internally. No formula can directly predict the optimal value — real pipeline behavior depends on instruction mix, bank conflicts, register pressure, and other factors that are difficult to model analytically. Profile-guided tuning is the only reliable method.

Exercise 5: Roofline Model Analysis (interview question)

Given: GPU NVIDIA H100 SXM; BF16 Tensor Core peak throughput 989 TFLOPS; HBM bandwidth 3.35 TB/s; Arithmetic Intensity (AI) = FLOPs / Bytes_accessed.

Questions: (1) Where is the ridge point? (2) Classify the following kernels: GEMM [4096,4096]×[4096,4096] (AI=4096), LayerNorm [32, 2048, 4096] (AI≈5), Softmax [32, 32, 2048, 2048] (AI≈3), element-wise ReLU (AI=0.25); (3) What are the optimization strategies for memory-bound vs compute-bound kernels?

Solution:

Summary: Ridge point = 295 FLOPs/Byte; GEMM (AI=4096) is compute-bound; LayerNorm (AI≈5), Softmax (AI≈3), and ReLU (AI=0.25) are all memory-bound. In LLM inference, the vast majority of non-GEMM kernels are memory-bound — which is exactly why Flash Attention and kernel fusion are so impactful.

Exercise 6: Shared Memory Bank Conflicts (interview question)

Given: Shared Memory has 32 banks, each 4 bytes wide; 32 threads in a warp access Shared Memory simultaneously; multiple threads accessing different addresses in the same bank → bank conflict (serialized); multiple threads accessing the same address in the same bank → broadcast (no conflict).

Questions: (1) Thread i accesses address i × 4 — how many bank conflicts? (2) Thread i accesses address i × 128 — how many bank conflicts? (3) Design a padding strategy to eliminate bank conflicts when accessing a 32×32 float matrix stored in Shared Memory by column.

Solution:

Interview key point: Bank conflicts are the biggest Shared Memory performance pitfall. In GEMM tiling, if the A tile is loaded row-by-row but accessed column-by-column (transposed access pattern), performance can drop several-fold without padding. Triton and CUTLASS both include built-in swizzle/padding mechanisms to handle this automatically.

Exercise 7: CUDA Graph Applicability + Quantifying the Benefit (interview question)

Given: an LLM decode step contains 200 small kernels; average compute time per kernel = 15 µs; kernel launch overhead without CUDA Graph = 5 µs per kernel.

Questions: (1) Without CUDA Graph — what is the total time, and what fraction is launch overhead? (2) With CUDA Graph — what is the total time, and what is the speedup? (3) If some kernels have dynamic shapes, can CUDA Graph still be used? How do SGLang/vLLM handle this?

Solution:

Summary: Without graph 4 ms, launch overhead is 25%; with graph ~3 ms, 1.33× speedup; dynamic shapes are handled by pre-compiling multiple graphs + padding — standard practice in SGLang/vLLM.

Interview follow-up: In the decode phase, individual kernels are very small (seq_len=1), so launch overhead makes up a larger fraction and CUDA Graph pays off more. This is why virtually every inference framework uses CUDA Graphs for decode but not for prefill (where kernels are large enough that launch overhead is negligible).

Exercise 8: Occupancy vs. Performance (interview question)

Given: a kernel uses 64 registers/thread and 48 KB shared memory/block; H100 SM resources: 65,536 registers/SM, 228 KB shared memory/SM, max 2,048 threads/SM, max 32 blocks/SM.

Questions: (1) Considering only the register constraint, what is the maximum number of threads per SM? (2) Considering only the shared memory constraint, what is the maximum number of blocks per SM? (3) Assuming 256 threads/block, what is the actual occupancy? (4) Does higher occupancy always mean better performance? Give a counterexample.

Solution:

Summary: Register constraint allows at most 1,024 threads (4 blocks × 256); Shared Memory constraint also limits to 4 blocks; occupancy = 50%; higher occupancy does not always mean better performance! GEMM and other compute-bound kernels deliberately use large register files for data reuse, sacrificing occupancy to achieve higher actual throughput.

Interview key point: NVIDIA’s official documentation explicitly states “higher occupancy does not always equate to higher performance.” In practice, use ncu (Nsight Compute) to profile and determine whether the bottleneck is latency hiding or instruction throughput. cuBLAS’s most optimized GEMM kernels typically run at only 25–50% occupancy.
