GPU Anatomy and LLM Token Dataflow

2026-06-03
gpu h100 memory-hierarchy llm-inference mlsys

To understand why LLM inference is slow and where the bottleneck actually is, you first need to see the complete path a single token takes through GPU hardware. This post starts from the full H100 die, goes through SM internals and the memory hierarchy, all the way to the dataflow from token input to output — with interactive diagrams throughout.

Part 1: Full GPU die overview

The H100 SXM is a massive 814mm² chip containing 132 SMs, 80 GB HBM3, and 3.35 TB/s of bandwidth. Below is an interactive GPU die diagram — click any component (HBM, Memory Controller, L2 Cache, Crossbar, SM, NVLink) to see a detailed description:

Part 2: SM (Streaming Multiprocessor) internals

Each SM is the GPU’s fundamental compute unit, containing Tensor Cores, CUDA Cores, SRAM, and schedulers.

Warp Scheduler × 4

Each SM has 4 Warp schedulers, each managing multiple Warps (groups of 32 threads). When a Warp is waiting on memory, the scheduler instantly switches to another ready Warp (latency hiding). Each SM can manage up to 64 Warps simultaneously = 2048 threads.

Tensor Cores × 4 (4th Gen)

Hardware units designed specifically for matrix multiplication. Each Tensor Core can compute one 4×4 matrix FMA per cycle, supporting FP16, BF16, FP8, and INT8 formats. Nearly all Linear layers in LLMs are computed here. Inputs are read from the Register File; results are written back to registers.

CUDA Cores (FP32) × 128

General-purpose floating-point ALUs. Handle element-wise operations: addition, RMSNorm, GeLU/SiLU activation, softmax, RoPE positional encoding, etc. 1 FP32 FMA per cycle per core. Far more flexible than Tensor Cores but much slower (extremely inefficient for matrix multiplication).

Shared Memory / L1 (SRAM) — 228 KB

The SM’s high-speed scratch space, explicitly managed by the programmer. The heart of Flash Attention: load K, V in tiles into SRAM, then complete + softmax + entirely in SRAM, avoiding writes back to HBM. Bandwidth ~30 TB/s (9× HBM), latency ~30 cycles. Size is the primary constraint — at only 228 KB, it can’t hold the entire KV Cache.

Register File — 256 KB

Each thread’s private ultra-fast storage. Tensor Cores and CUDA Cores read/write operands directly from here. Latency ~1 cycle, bandwidth ~60 TB/s. Each thread can use up to 255 32-bit registers. Register pressure: use too many → fewer Warps can run simultaneously → worse latency hiding.

Load/Store Units × 32

Responsible for all memory read/write operations. Every memory request goes through: (1) check L1/Shared Memory first; (2) miss → check L2 Cache; (3) miss → go to HBM. 32 LD/ST units means up to 32 memory transactions can be issued per cycle. During LLM decode, most time is spent waiting for these units to move weights from HBM.

Three key intuitions

Tensor Core vs CUDA Core: Tensor Cores are specialized for D = A×B + C matrix FMA — one 4×4 matrix per cycle. CUDA Cores do one scalar multiply-add per cycle. For a 4×4 matrix multiplication: Tensor Core takes 1 cycle; CUDA Cores need 64 multiplies + 48 adds. So LLM Linear layers all use Tensor Cores, and element-wise operations use CUDA Cores.

Why SRAM matters so much: HBM is 80 GB but only 3.35 TB/s; SRAM is 228 KB per SM but ~30 TB/s. Flash Attention’s secret is keeping data in SRAM for computation as much as possible, avoiding round-trips to HBM. Naive Attention writes the result back to HBM, then reads it back to do softmax; Flash processes everything in tiles entirely within SRAM, reading K and V from HBM only once.

Warps and latency hiding: HBM read latency is ~400 ns ≈ hundreds of clock cycles. If only 1 thread group is running, the GPU spends most of its time waiting on memory. The solution: put 64 Warps per SM — when one Warp waits on memory, the scheduler instantly switches to another ready Warp. This is the GPU’s core design philosophy — trade concurrency for latency.

Part 3: Memory hierarchy

From the farthest HBM to the nearest registers — the closer, the faster, but also the smaller:

Level Capacity Bandwidth Latency Contents
HBM3 (VRAM) 80 GB 3.35 TB/s ~400 ns Model weights + KV Cache + activations + optimizer state
L2 Cache 50 MB ~12 TB/s ~150 ns Shared by all SMs; caches RoPE tables, small weights, frequently accessed KV
Shared Memory / L1 (SRAM) 228 KB / SM ~30 TB/s ~30 ns SM-private, programmer-managed, Flash Attention workspace
Register File 256 KB / SM ~60 TB/s ~1 ns Thread-private, direct operand source for compute units
Tensor + CUDA Cores 989 TFLOPS FP16 / ~67 TFLOPS FP32 — — Read operands from registers → compute → write back to registers

The fundamental tension: Tensor Cores need data fed at 989 TFLOPS, but HBM can only deliver 3.35 TB/s.

This is H100’s arithmetic intensity roofline. LLM decode GEMV is only ~1–2 FLOPs/Byte — Tensor Cores are idle 99% of the time waiting on HBM!

Part 4: Token dataflow

The interactive diagram below walks step by step through a single token’s complete journey through GPU hardware from input to output (LLaMA-70B decode). Each step highlights the active HBM regions, SMs, and caches, explaining where data comes from, where it goes, and what compute units it passes through:

Key observations from the full flow:

  • Steps 2 / 5 / 8 / 10 (various Projections) are all GEMVs: weights vastly outnumber activations, so weights are streamed from HBM → Tensor Cores for computation — this is the root cause of memory-bound behavior.
  • Step 4 (Attention / Flash Decoding): the score matrix is never written back to HBM; K and V are read once, producing a single output vector.
  • Step 7 (FFN Gate + Up) is the largest single weight read in the entire forward pass: W_gate + W_up = 896 MB.

Total weight reads per layer: ~1.86 GB (Attention 512 MB + FFN 1.34 GB). For a 70B model with 80 layers, generating one token requires reading ~148 GB of weights + ~1.3 GB of KV Cache ≈ 150 GB. Theoretical time:

In practice around 55–70 ms (various overheads). The final output is just 1 integer (next_token_id) — that’s the token you see appearing one character at a time. This token then re-enters Step 0 to begin the next decode iteration.
