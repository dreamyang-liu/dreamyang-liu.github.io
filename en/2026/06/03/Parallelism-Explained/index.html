GPU Parallelism Strategies Explained: TP / PP / EP / SP

2026-06-03
parallelism tensor-parallel pipeline-parallel expert-parallel sequence-parallel mlsys

When training or running inference on large models, a single GPU’s memory and compute are nowhere near enough. This post systematically covers four mainstream parallelism strategies — Tensor Parallelism, Pipeline Parallelism, Expert Parallelism, and Sequence Parallelism — with interactive animations for the key mechanisms.

Tensor Parallelism (TP)

Split the weight matrix inside a single layer, have each GPU compute a portion, then AllReduce to merge the results.

Column Parallel: Split the weight matrix by columns

Take the original weight matrix and split it in half by columns, one half per GPU:

  • GPU 0 holds
  • GPU 1 holds

Each GPU multiplies the full input by its own half of the weights, producing different columns of the full result.

Interactive animation: full MLP layer TP computation (Megatron-LM style)

The essence of Megatron-LM is Column Parallel → GeLU (no communication) → Row Parallel → AllReduce — the entire MLP forward pass needs only 1 AllReduce. The animation below walks through the full computation flow on two GPUs step by step:

Key takeaway: The entire MLP forward pass needs just 1 AllReduce!

Why: Column Parallel outputs are different columns of the full result. GeLU is element-wise and doesn’t need the full vector. Row Parallel outputs have the same shape but different values — summing them gives the full result → AllReduce.

Compared to the naive approach: If both Linear layers used Column Parallel, you’d need an AllGather in the middle to reassemble the full result before the second multiply. Megatron’s Column→Row combination cleverly skips that intermediate communication.

Typical config: TP = 8 (8 GPUs on a single node over NVLink at 900 GB/s), 1 AllReduce per layer forward, 1 AllReduce per layer backward.

Pipeline Parallelism (PP)

Split the model by layers, with each GPU (or group of GPUs) responsible for a contiguous set of layers. Data flows through like an assembly line.

Model split by layers across 4 stages

Stage GPU Layers
Stage 0 GPU 0 Layer 0-7 + Embedding
Stage 1 GPU 1 Layer 8-15
Stage 2 GPU 2 Layer 16-23
Stage 3 GPU 3 Layer 24-31 + LM Head

Interactive animation: 1F1B pipeline schedule

1F1B (One Forward One Backward) scheduling has each stage alternately execute one forward and one backward micro-batch in steady state, maximizing GPU utilization. The animation below shows the forward/backward flow for 4 GPUs and 4 micro-batches (dark = Forward, light = Backward, blank = Pipeline Bubble):

Key takeaway: PP splits by layer — each stage only stores the weights and activations for its own layers, and stages communicate activation tensors over the network.

Communication volume: Only activation tensors are transmitted (much smaller than AllReduce), works across nodes.

Downside: Pipeline bubbles (GPUs waiting idle); you need enough micro-batches to fill the pipeline.

Typical config: PP = 4–16, cross-node via InfiniBand / RoCE.

Expert Parallelism (EP)

Exclusive to MoE models: each Expert lives on a different GPU, and the Router decides which Expert to send each token to.

The animation below shows the full dispatch flow: tokens go through the Router to compute gating scores, get sent via All-to-All to the target Expert’s GPU, are computed, then sent back:

EP vs TP in MoE layers

Approach Sharding Communication Load
TP=8 (shard inside each Expert) Each GPU holds 1/8 of every Expert AllReduce per layer (large) Balanced (same amount per GPU)
EP=8 (each Expert on its own GPU) Each GPU holds 1 full Expert All-to-All (token dispatch) Potentially unbalanced (hot Experts get more traffic)

Key takeaway: EP places different Experts on different GPUs and exchanges tokens via All-to-All.

Advantage: Naturally matches the MoE structure — each GPU only needs to store weights and optimizer state for one Expert.

Challenge: All-to-All volume depends on batch size and number of experts; some GPUs sit idle when load is unbalanced.

Typical config: EP = number of Experts or a factor of it (EP=8 for 8 experts).

Sequence Parallelism (SP)

Split along the sequence dimension. Operations that TP can’t shard (LayerNorm, Dropout) are distributed by SP.

The problem: TP can’t shard LayerNorm and Dropout

Operations inside a Transformer layer fall into two categories:

  • TP-shardable (split along the hidden dimension): Self-Attention, FFN / MLP
  • Requires the full hidden dimension (TP can’t shard): LayerNorm, Dropout + Residual

SP’s solution: shard these operations along the sequence dimension

The input sequence [batch, seq_len, hidden_dim] is split along the seq_len dimension across two GPUs:

  • GPU 0: first half of the sequence (e.g., first 4 tokens) → does LayerNorm / Dropout locally
  • GPU 1: second half of the sequence (e.g., last 4 tokens) → does LayerNorm / Dropout locally

Because LayerNorm / Dropout both operate independently per token along the hidden dimension, splitting by sequence doesn’t affect correctness at all.

TP + SP together: one full layer’s flow

Key insight: . SP splits these two steps apart, and they naturally complete the communication right at the TP↔SP boundary — total communication volume is unchanged!

Key takeaway: SP is not an independent parallelism strategy — it’s a complement to TP. TP shards Attention/FFN; SP shards LayerNorm/Dropout.

What it saves: Activation memory. Without SP, every GPU stores LayerNorm activations for the full sequence; with SP, each GPU only stores seq_len/TP worth of activations.

Communication overhead: AllGather + ReduceScatter replaces the original AllReduce — same total volume, but activation memory is reduced to 1/TP.

Typical config: SP = TP (always enabled together; this is Megatron-LM’s default behavior).

Summary comparison

EP Expert index All-to-All Medium (token dispatch) MoE layers, cross-node 8–64
