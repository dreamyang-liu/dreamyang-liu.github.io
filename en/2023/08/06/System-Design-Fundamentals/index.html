System Design Theory

CAP Theorem

The CAP theorem, also known as Brewer’s theorem, states that a distributed database system can only guarantee two of the following three properties: Consistency, Availability, and Partition Tolerance. A system that prioritizes availability over consistency may respond with stale data.

Partition Tolerance

In CAP theory, Partition Tolerance refers to a system’s ability to continue serving requests even when a network partition occurs.

A network partition is when the nodes in a system are split into two groups and the network communication between them is cut off. In this situation, a distributed system may exhibit one of two behaviors:

  1. Refuse to serve requests — the entire system becomes unavailable and invisible to users.

  2. Continue serving at the cost of consistency — the system remains visible to users but may return inconsistent data.

Partition Tolerance means the system can tolerate network partitions and keep serving without completely breaking down. According to the CAP theorem, a system cannot simultaneously guarantee Consistency, Availability, and Partition Tolerance — at most two can be satisfied at once.

So a Partition-Tolerant system typically sacrifices data consistency to maintain service availability. This may mean allowing stale reads or tolerating conflicting data across partitions. This is an acceptable trade-off in many large-scale distributed systems.

A classic example of Partition Tolerance is the DNS system.

DNS uses a distributed tree structure where a single domain name is served by multiple DNS servers. When a network partition occurs, the following may happen:

  1. Users in certain regions cannot reach some DNS servers, but can still reach others and get a name resolution result.

  2. Different DNS servers return different resolution results (inconsistent IP addresses), but users still receive a response.

This is the Partition Tolerance behavior DNS exhibits. When a network partition occurs, DNS chooses to accept the risk of returning inconsistent data rather than stopping all responses.

Another example of Partition Tolerance is distributed caching systems like Memcached. When nodes lose contact with each other, data across different partitions may be inconsistent, but each partition can continue using its local cache — the overall system does not stop serving.

These systems all adopt the design philosophy of “allow dirty reads” or “tolerate brief inconsistency” to achieve Partition Tolerance. For most applications, returning slightly stale or inconsistent data is still preferable to the entire system being completely unavailable.

Modern Distributed System Components

Load Balancer

A load balancer is the entry point for web applications. It distributes incoming client traffic across different worker nodes/servers. It helps:

  1. Avoid overloading a single server
  2. Redirect requests to healthy servers when one is unavailable.

Load balancers play an important role in enabling a system to scale horizontally. AWS provides the following load balancer services:

  1. Classic Load Balancer: primarily used to distribute traffic across EC2 instances
  2. Application Load Balancer: more flexible; the default choice.
  3. Network Load Balancer
  4. Gateway Load Balancer

CDN

A Content Delivery Network (CDN) is a fast file delivery service provided by a third party. By exposing a single endpoint, the CDN service automatically routes requests to the nearest server to fetch static files. It is mainly used to serve static assets such as HTML, JavaScript files, and images. It can also host other files like videos and archives. It can:

  1. Offload traffic from web servers
  2. Speed up file retrieval by fetching from the nearest server.

CDNs require a TTL (Time to Live) to be configured. If the TTL is set too short, the cache will need to be refreshed from the origin frequently, increasing data transfer costs. If the TTL is set too long, clients may receive stale files. TTL should be set based on the system’s requirements.

DNS

The Domain Name System (DNS) is a database that translates domain names into Internet Protocol (IP) addresses. DNS maps the names people use to locate websites to the IP addresses computers use to locate those websites.

Web Tier

The web tier primarily refers to web services. Web services mainly contain business logic — for example, fetching data from a database and returning it to the user, or submitting an order on behalf of a user. Ideally, the web tier should be stateless, as this makes it much easier to scale horizontally.

Data Tier

The data tier primarily refers to databases or persistent storage. “Persistent” means data is not lost even when the server goes down. In contrast, some in-memory caching systems will lose all data if the server restarts. As data has grown increasingly complex, a wide variety of database systems have been developed to accommodate different use cases.

  1. Relational databases
  2. NoSQL (Not Only SQL)

Describing databases in full detail here would be too ambitious — we will cover them in a dedicated post.

Cache Tier

The cache tier exists because querying a database is an expensive operation. Some requests can also be expensive in other ways, such as running a model for computation. Thanks to the principle of locality, we know that processors tend to repeatedly access the same set of memory locations over a short period of time. This means the same data may be needed multiple times within a short window, making a cache tier very useful in production systems. The cache operates as middleware within the system and can be scaled independently. It also introduces its own set of challenges, such as cache stampede, cache misses, and data synchronization. Like the data tier, we will cover it in a dedicated post.

Message Queue

Sometimes we may wonder about service call chains — how do these subsystems scale independently? For example, if Service A tries to call Service B and Service B is unavailable at the moment, Service A must wait, or the request from the client will be lost. We might want something that abstracts the input producers from the result consumers. This is where message queues come in.

A message queue acts as a temporary storage service. Producers can publish messages to the MQ regardless of whether consumers are running. At the same time, consumers can consume messages from the MQ regardless of whether producers are running.
