4.1 Request Lifecycle

An LLM inference request passes through several stages from user input to final output. In SGLang, this process is carefully designed as an efficient pipeline: TokenizerManager → Scheduler → TpModelWorker → DetokenizerManager.

The animation below shows a request flowing through five stages: Tokenize → Schedule → Prefill → Decode → Detokenize.

Stage Breakdown

Stage Operation Bottleneck SGLang Optimization
Tokenize Convert user input text to a sequence of token IDs CPU-intensive Async tokenization overlapped with GPU computation
Schedule Assign requests to batch slots, manage priorities Scheduling latency Continuous batching + priority queue
Prefill Process all prompt tokens in parallel, populate KV cache Compute-bound Chunked prefill, radix cache reuse
Decode Autoregressive token-by-token generation Memory bandwidth PageAttention, efficient KV cache access
Detokenize Convert generated token IDs back to text CPU-intensive Incremental detokenization + streaming

The Essential Difference Between Prefill and Decode

The prefill stage is compute-bound (high compute volume; GPU compute units are the bottleneck): all prompt tokens can compute attention in parallel, leading to dense matrix operations.

The decode stage is memory-bandwidth-bound (frequent KV cache reads; HBM bandwidth is the bottleneck): only one token is generated per step, but the full KV cache must be read each time.

Performance Metrics: TTFT and TPOT

Metric Full Name Meaning Determining Factor
TTFT Time To First Token Latency from request submission to the first output token Prefill speed + queuing time
TPOT Time Per Output Token Generation interval for each subsequent token (the “typing speed” perceived by users) Decode speed

User experience: 1000 / TPOT = tokens/sec. TPOT=50 ms → 20 tok/s (smooth), TPOT=200 ms → 5 tok/s (choppy).

How GPU Memory Is Actually Allocated

KV cache is not the only tenant — during inference, a GPU’s memory is divided among several “residents.” What exactly is that 10% reserved by vLLM’s gpu_memory_utilization=0.9? Enumerating every item makes it possible to calculate how many concurrent requests fit, and when OOM happens.

Item Purpose Size (70B, TP=8, FP16, per GPU) Grows with concurrency / seq len?
Weights Model parameters — Linear/Embedding/LayerNorm 140 GB / 8 = 17.5 GB ✗ Fixed
KV cache K, V tensors for every past token, must be read during decode 0 — tens of GB ✓ The only item that grows linearly
Activations (peak single layer) Intermediate results of current forward layer (QKV / attn out / MLP) ~100 MB (decode) — ~1 GB (long prefill) ✓ Only during prefill
cuBLAS / cuDNN workspace GEMM kernel split-K / reduce staging buffers A few hundred MB per stream ✗ Allocated at startup
NCCL / RCCL communication buffers Send/receive staging for TP all-reduce / all-gather 100 MB – 1 GB ✗ Allocated at startup
CUDA graph memory vLLM captures one graph per batch size by default Hundreds of MB – 1+ GB ✗ Allocated at startup
PyTorch caching allocator fragmentation Unreturned / uncoalesced blocks from past allocations 0.5 – 2 GB ✗ Accumulates over time
CUDA driver / runtime baseline The baseline shown by nvidia-smi as soon as the process starts ~500 MB ✗ Fixed

Total non-KV-cache overhead for 70B per GPU ≈ 17.5 (weights) + 2–3 (workspaces/graph/fragmentation) + 0.5 (driver) ≈ 20 GB. On an 80 GB GPU that leaves roughly ~60 GB for KV cache + prefill spikes — which is why gpu_memory_utilization=0.9 reserves 8 GB as a buffer.

Key Caveats for Each Item

Weights — After TP sharding, each GPU holds only 1/TP, but embeddings are typically not sharded (the vocabulary is small enough that all-gathering after sharding would cost more). A 70B vocabulary of 32k × hidden 8192 × 2 bytes ≈ 0.5 GB — unsharded, not a problem.

Activations — These are the dominant term in training (70B training activations alone reach 145 GB, as covered in the previous chapter); during inference they sit at ~100 MB. The reason: inference does not store gradients, so each layer can be discarded as soon as it finishes; FlashAttention avoids materializing the O(s²) attention scores. The two scenarios where this can blow up:

  • Ultra-long prefill: a s=128k prompt requires 10·128k·8192/8 ≈ 1.3 GB per layer.
  • Large prefill batch: doubling the batch doubles the activation footprint.

vLLM’s --max-num-batched-tokens cap is specifically designed to bound this prefill peak.

cuBLAS workspace — Running torch.cuda.memory_summary() often reveals several hundred MB of Allocated by CUDA libs. This is primarily cuBLAS’s GEMM split-K reduction buffer — large matrix multiplications partition the K dimension into chunks, compute each chunk independently, then reduce; the intermediate results need staging. Each CUDA stream allocates independently; multiple streams multiply this footprint.

NCCL buffer — With TP=8, the staging memory for all-reduce per GPU ≈ hidden × bs × seq × 2 bytes × 2 (recv+send). NCCL expands this on demand; large batches cause more inflation. You can cap it with environment variables like NCCL_BUFFSIZE=8388608.

CUDA graph — vLLM captures one graph for each common batch size (1, 2, 4, 8, 16, 32, ...) to eliminate kernel launch overhead. Each captured graph carries its own ~tens-of-MB workspace; the cumulative size is substantial. --enforce-eager disables this and saves 1–2 GB, at a cost of 10–20% decode throughput.

Allocator fragmentation — PyTorch’s caching allocator carves large blocks for small requests and may not be able to coalesce freed blocks. Long-running serving processes typically use 1–2 GB more than they did at startup, invisibly. PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True can substantially mitigate this.

Concrete Memory Budget: 70B on 8 × 80 GB H100

When Should You Lower gpu_memory_utilization?

Symptom Real Cause Not Caused By
OOM at startup weights + workspaces already exceed 90% Activation growth
OOM during prefill burst Long prompts / large prefill batch causes activations to spike to GB scale temporarily KV cache growth (KV cache grows gradually, not instantly)
OOM after long runtime Allocator fragmentation accumulates Weights / KV cache

Lowering gpu_memory_utilization (e.g., 0.9 → 0.85) primarily provides headroom for workspaces + prefill spikes, and has little to do with steady-state activations.

One-Line Intuition

Training memory = (weights + grads + optimizer) (shardable with ZeRO) + activations (grow with batch×s², must be compressed with checkpointing + TP + SP)

Inference memory = weights (static) + KV cache (grows linearly with concurrency, the only tunable pool) + workspace (allocated at startup) + activation spike (only during prefill)

What gpu_memory_utilization is really reserving space for is workspace + spike, not steady-state activations. Smaller value → smaller KV cache pool → fewer concurrent requests fit; larger value → more likely to OOM during a prefill burst.

Where Activations Actually Live in the Transformer

The table above vaguely says “intermediate results” for activations, but knowing exactly which tensors, and their shapes, determines how large a prefill spike will be and what FlashAttention saves. Walk through the forward pass of a pre-LN transformer block with every activation labeled:

Each ★ is a large contributor; everything else is at the (b, s, h) scale. Grouping activations by order of magnitude:

Scale Shape Which tensors Size per instance (70B, b=1, s=2048)
O(b·s·h) (b, s, h) LN i/o, Q/K/V, attn_out, residual sum, LN2 i/o Each ≈ 34 MB
O(b·s·4h) (b, s, 4h) MLP up output, GeLU output Each ≈ 134 MB (4× larger)
O(b·n_h·s²) (b, n_h, s, s) Attention scores, softmax output Each ≈ 1.0 GB (s² explosion)

At s=8192, a single attention score tensor is 17 GB per layer — it overwhelms everything else. This is why long-context training almost universally requires FlashAttention.

What FlashAttention Eliminates

FlashAttention’s core: scores and softmax outputs are never materialized to HBM, computed in SRAM tile-by-tile and fed directly to @ V. So with FA:

  • ★ The two O(s²) items: disappear from the activation list (backward uses the same tiled recomputation — see FlashAttention backward)
  • Everything else is unchanged

Megatron’s Act per layer = 34·s·b·h + 5·a·s²·b formula has the 5·a·s²·b term eliminated by FA. This is why Megatron’s selective activation recomputation recomputes only attention scores by default — the single largest item, with the cheapest recompute cost (~10% extra FLOPs saves ~80% of activations).

Two “Non-layer” Activations at the Boundaries

Tensor Shape Size (70B, b=1, s=2048) Notes
Input embedding output (b, s, h) 34 MB One copy; must be retained during training (needed for embedding backward)
Output logits (b, s, vocab) LLaMA-2 vocab=32k: 130 MB; LLaMA-3 vocab=128k: 524 MB Larger than a single-layer activation; a common OOM hotspot
Loss softmax intermediate (b, s, vocab) Same as above Commonly eliminated with fused CE kernels (Liger/Apex)

The output logits tensor is the biggest single-point contributor — this is why fused cross-entropy is almost mandatory when training long-context + large-vocabulary models (the approach is identical to FlashAttention: avoid materializing the intermediate).

Training vs. Inference: Which Activations Survive, Which Are Freed

Training (backward needs them) Inference (no backward)
LN i/o / Q / K / V / MLP intermediates Kept until backward completes Discarded as soon as a layer finishes; memory reused by the next layer
Attention scores (O(s²)) Without FA: stored; with FA: not stored Without FA: temporary; with FA: not stored
Output logits Kept until loss backward Discarded immediately (one token generated is enough)
Total live activations simultaneously All layers × all items above (without checkpointing) Roughly only the current layer’s intermediates

This is why training activations are ~150 GB/GPU (70B) while inference activations are ~100 MB/GPU — not because inference “saves” anything special, but because inference simply does not need to retain them all before backward begins.

One-Line Intuition

“Short” activations (O(b·s·h)): like hidden states passing through a pipeline stage by stage, one copy each, not huge but numerous.

“Wide” activations (O(b·s·4h)): the MLP intermediate expands to 4×; these are the largest non-O(s²) items per layer and contribute the most to total activation memory.

“Square” activations (O(b·n_h·s²)): the attention score matrix — explodes as soon as s grows. FlashAttention exists specifically to eliminate them.

4.2 Continuous Batching vs. Static Batching

Traditional static batching waits for every request in a batch to finish generating before starting on the next batch, causing severe GPU resource waste. Continuous batching dynamically adds and removes requests so that the GPU stays highly utilized at all times.

The animation below compares GPU utilization between the two batching strategies (red = wasted slots):

Core Implementation of Continuous Batching

Key design points:

  • Iteration-level scheduling: requests may join or leave after every decode iteration
  • No padding required: requests of different lengths are handled efficiently via PageAttention
  • Memory-aware scheduling: new requests are only admitted when the KV cache pool has sufficient space
  • Priority support: shorter requests complete first, reducing average latency

Performance Comparison

Metric Static Batching Continuous Batching Improvement
GPU utilization 30–50% 85–95% ~2×
Throughput (tokens/s) Baseline 2–3× Significant
Average latency High (waits for longest request) Low (timely release) 50–70%↓
Tail latency (P99) Very high Controllable Major improvement

4.3 KV Cache Management

PageAttention: Virtual Memory for the KV Cache

Inspired by the OS paged memory model. PageAttention divides the KV cache into fixed-size pages (blocks) and uses a page table to implement non-contiguous physical memory mappings, solving the memory fragmentation problem in traditional approaches.

Radix Cache: Prefix-Sharing Tree

One of SGLang’s core innovations. When multiple requests share the same system prompt or prefix, the radix cache shares KV cache via a tree structure, avoiding redundant computation.

Below is an interactive radix tree: click the buttons to add requests and watch how shared prefixes are reused and how new requests match the longest cached prefix:

Radix Cache Implementation

Advantages of radix cache:

  • Prefix sharing: requests with the same system prompt share KV cache, saving GPU memory
  • Automatic matching: new requests automatically find the longest cached prefix, skipping already-cached prefill computation
  • LRU eviction: reclaims infrequently used cache entries when memory is tight
  • Multi-turn acceleration: KV from earlier turns in a multi-turn conversation is cached and reused

4.4 Scheduler Design

The Scheduling Tension Between Prefill and Decode

Prefill and decode have fundamentally different compute characteristics; efficiently scheduling both on the same GPU is a core challenge:

Property Prefill Decode
Compute profile Compute-bound (large matmul) Memory-bound (KV cache reads)
Latency sensitivity Affects TTFT Affects TPOT
Token count Hundreds to thousands 1 per step
GPU utilization pattern High compute density High bandwidth demand

Preemption: What to Do When Memory Runs Out

When KV cache memory is insufficient to accommodate a new request, some running requests must be “evicted” to free space.

Preemption strategies:

Strategy Approach Recovery Speed Extra Cost
Swap to CPU Move KV cache to CPU RAM Fast (PCIe copy back) Requires CPU memory + PCIe bandwidth
Recompute Discard KV cache, re-prefill on recovery Slow (recompute) No extra memory, but wastes compute
Kill Terminate the request entirely N/A Bad user experience

Who should be preempted?

Congestion control mechanism — analogous to TCP congestion control — when system load is high:

  1. Monitor waiting queue length and KV cache utilization
  2. When thresholds are exceeded, throttle new prefill admissions
  3. In extreme cases, trigger preemption (pause low-priority requests)
  4. Gradually restore admission rate as load decreases

4.5 Quantization Overview

Quantization reduces model memory footprint and compute overhead by lowering the numerical precision of weights and/or activations. For LLM inference, it is a key technology for deploying large models within constrained GPU memory budgets.

Common Quantization Strategies

Method Weight Precision Activation Precision Characteristics
W16A16 FP16 FP16 Baseline, lossless
W8A8 (FP8) FP8 E4M3 FP8 E5M2 Natively supported on H100, nearly lossless
W4A16 (GPTQ/AWQ) INT4 FP16 Weight-only quantization, activations at high precision
W4A8 INT4 INT8 Aggressive compression, requires calibration

FP8 quantization (natively supported by H100 Tensor Cores):

Mixed precision strategy. Not all layers are well-suited for quantization. A typical approach:

  • Attention QKV/O projections: suitable for FP8 quantization
  • FFN layers: suitable for INT4 weight quantization (large parameter count)
  • LayerNorm: keep at FP32 (precision-sensitive)
  • First and last layers: typically kept at high precision

4.6 Speculative Decoding

The core idea of speculative decoding: use a small, fast draft model to generate multiple candidate tokens, then use the large target model to verify those tokens in parallel. Because verifying N tokens costs roughly the same as generating 1 token (both require one forward pass), sufficiently high acceptance rates yield significant speedups.

4.7 Constraint Decoding

Structured Output Generation

In practice we often need an LLM to produce output in a specific format (JSON, SQL, code, etc.). Constraint decoding guarantees that the output always conforms to a given grammar by dynamically masking illegal tokens during generation.

Core approaches:

  • CFG (Context-Free Grammar) guidance: define grammar rules; only legally next tokens are allowed during decoding
  • JSON Schema constraints: dynamically compute a valid token mask from the JSON Schema
  • Regex constraints: filter tokens using a regular-expression state machine
  • FSM (Finite State Machine): compile the constraint into an FSM for efficient legal-token lookup

Optimizations in SGLang: SGLang combines FSM state transitions with the radix cache — requests sharing the same constraint rule share FSM state and precomputed token masks, avoiding redundant compilation. Additionally, through jump-forward decoding, when the FSM determines that there is only one legal path ahead (e.g., the quotation marks around a JSON key), model inference can be skipped and the token emitted directly.

4.8 Model Loading Pipeline

The Complete Flow from Disk to GPU

Loading a large model involves several steps: weight file parsing → weight mapping → tensor-parallel sharding → GPU memory allocation → quantization conversion.

Key optimizations:

  • Streaming load: load one shard file at a time to avoid CPU memory peaks
  • Async H2D transfer: overlap CPU → GPU transfer with CPU loading of the next shard
  • Safetensors format: zero-copy memory-mapped files, load specific tensors on demand
  • Pre-computed sharding: TP plan determined upfront to avoid runtime allocations
