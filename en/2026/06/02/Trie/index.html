Trie (Prefix Tree)

2026-06-02
Data Structures Strings

Each node stores one character, and the path from root to leaf spells out a complete string. Strings with a common prefix share the leading nodes — that’s why it’s called a “prefix tree.” Both insert and lookup run in , independent of how many words are in the dictionary.

Intuition — Shared Prefix, Shared Nodes

A hash set can look up a single word in , but it can’t answer “give me all words that start with app.” A trie spreads characters across a tree: strings that share a prefix follow the same path, and branching only happens at the first position where characters differ.

After inserting apple, app, ant, bee:

  • apple and app share the three nodes a -> p -> p;
  • ant branches off after a;
  • bee starts an entirely separate subtree.

Three things to internalize at once:

  1. Each edge represents one character; each node represents the prefix accumulated so far. Nodes don’t store the whole string.
  2. is_end (shown as # in the diagram) is mandatory. Without it you can’t tell “app was explicitly inserted” from “app is just a waypoint on the path to apple.”
  3. Query cost is , where is the length of the query string. Whether the dictionary has ten thousand or a hundred million words is completely irrelevant.

A trie isn’t about looking up a single word faster — it’s about batch operations over prefixes. That’s the only reason it exists.

Animation — Watching Characters Land

The animation below inserts apple, app, ant, bee one by one, then demonstrates search("app") and search("ap"). Focus on three things:

  • Shared prefix: apple already built the three nodes a-p-p; inserting app creates no new nodes, it just stamps a # on the last p.
  • The # marker: once app‘s # is placed, search("app") returns True; but search("ap") — even though the path exists — returns False because p has no #. It’s a prefix, not a word that was actually inserted.
  • Node count ≠ total character count: the four words have 13 characters in total, but the tree has only 11 nodes (the a-p-p segment is shared). The denser the dictionary, the greater the savings.

Advanced — 01-Trie for Maximum XOR

LC 421. Maximum XOR of Two Numbers in an Array: given an array of integers, find .

The naive approach is . A 01-Trie brings it down to . The core idea in one sentence: treat each integer as a 30-bit binary string and insert it into a trie — the character set is just {0, 1}, hence “01-Trie.”

Why does this solve maximum XOR? XOR’s defining property: bits that differ contribute 1. Starting from the most significant bit, greedily try to take the branch that is the opposite of the current bit — if that branch exists, this bit contributes 1; otherwise fall back. Because high bits outweigh all lower bits combined, the greedy is optimal.

This problem is the signature 01-Trie application. Memorize the pattern — “from high bit to low bit + greedy take the opposite branch” — and every variant (count pairs whose XOR falls in a range, maximum XOR subarray, etc.) is just a twist on this same template.

Applications

Tries aren’t just interview fodder — they show up throughout production systems:

  • Autocomplete / search-box suggestions: type a prefix, walk to its subtree, DFS to collect all words, rank by popularity.
  • Longest-prefix matching in IP routing: a routing table is essentially a binary trie; an incoming packet walks from root to leaf, matching the longest prefix it finds.
  • Spell-checking / fuzzy matching: DFS on the trie while allowing a small number of substitutions/insertions/deletions (edit distance) — much faster than scanning the full word list.
  • Sensitive-word filtering (Aho-Corasick): multi-pattern string matching; add failure pointers to a trie and scan a text once to find all patterns.
  • String XOR / bitwise extrema: see 01-Trie above.
  • Suffix tree / suffix array family: index all suffixes of a string for fast substring queries.

When to reach for a trie: any time a problem mentions “prefix,” “dictionary,” or “multi-pattern,” think trie first.

Memory Aid

One sentence: characters on the edges, prefixes on the paths, # at word endings.

Three things to burn into muscle memory:

Point Detail

Time complexity Insert/lookup both , independent of dictionary size
Common mistake End marker # is non-negotiable; omitting it makes prefixes and full words indistinguishable

Decision cheat sheet:

  • See “prefix” → Trie
  • See “multiple strings queried together” → Trie
  • See “maximum/minimum XOR” → 01-Trie
  • See “sensitive words / multi-pattern matching” → Aho-Corasick (Trie + failure pointers)

When writing the template, recite mentally: allocate node → walk to it → stamp the end marker. Three steps, never get it wrong.

Exercises

What specifically goes wrong without #?

After inserting apple, search("app") would return True — because the path a-p-p does exist. But app was never actually inserted, so this is a false positive. The role of # is to distinguish “a node that lies on some path” from “the endpoint of a word that was explicitly inserted.”

Why does the 01-Trie start from the high bit instead of the low bit?

The XOR result is a binary number, and the highest bit’s weight exceeds the sum of all lower bits (). So if you can secure a 1 in the high bit, you should always do so, even at the cost of all lower bits. Greedy from the low bit can be overturned by a single high bit.

How does a trie's memory footprint compare to a HashSet?

Each trie node must store a dict (or a length-26 array), which isn’t cheap. But the denser the dictionary (more shared prefixes), the more memory is saved: ten thousand English words share so many prefixes that the node count is far smaller than the total character count. A sparse dictionary (every word has a unique prefix) actually costs more memory than a HashSet.
