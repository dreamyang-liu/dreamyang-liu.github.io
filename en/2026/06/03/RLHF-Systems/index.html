1. RL Fundamentals Review

Markov Decision Process (MDP)

In the RLHF setting we model the LLM generation process as an MDP:

State Token sequence generated so far prompt + generated prefix
Action Next token sampled from the vocabulary
Policy LLM output distribution softmax over logits
Reward Reward Model score typically given only at end of sequence

Policy Gradient

The core idea of Policy Gradient: increase the probability of good actions, decrease the probability of bad ones.

Here is the Advantage Function (, measuring how much better a given action is than average), representing how much better action is in state relative to the average policy.

4. GRPO — Group Relative Policy Optimization

Core Idea: Eliminating the Critic Network

GRPO (proposed by DeepSeek) is built around one key innovation: estimating the advantage via relative comparisons within a group of rollouts, with no separately trained value function (critic).

For each prompt , generate responses , score each one, then normalize using the within-group mean and standard deviation.

5. Systems Design Challenges

Training + Inference Co-design

The biggest engineering challenge in RLHF systems: the same model weights must serve both training (backward pass) and inference (rollout generation).

The core tension:

  • Training needs: parameter sharding (FSDP/DeepSpeed), activation storage, gradient computation
  • Inference needs: Tensor Parallelism, KV Cache, continuous batching
  • The two require completely different storage layouts and parallelism strategies!

Common solutions:

Strategy Pros Cons
Colocate no network overhead memory contention, low utilization
Separate deployment each side can be optimized independently requires weight sync
Hybrid Engine dynamic switching complex to implement

6. veRL Architecture

Design Philosophy: Single Controller + Hybrid Engine

veRL (Volcano Engine RL) uses Ray as the distributed scheduling framework, with a single controller coordinating all components.

Core components:

  • Single Controller: one Python process manages the entire training loop
  • Actor Workers: run the policy model (FSDP sharded)
  • Rollout Workers: run the inference engine (vLLM/SGLang)
  • Critic Workers: run the value model
  • Reward Workers: run the reward model

veRL Training Loop:

  1. Controller sends prompts to Rollout Workers
  2. Rollout Workers generate responses using the current policy
  3. Reward Workers compute reward scores
  4. Critic Workers compute value estimates
  5. Controller computes GAE advantages
  6. Actor Workers execute the PPO update
  7. Sync new weights to Rollout Workers → back to 1

Key to the Hybrid Engine: veRL’s Actor Workers and Rollout Workers can be colocated on the same set of GPUs:

  • Training phase: GPUs do FSDP training
  • Rollout phase: offload optimizer states, switch to inference mode
  • Reduces the network overhead of weight synchronization

8. OpenRLHF

Open-Source RLHF Framework

OpenRLHF is the most widely used open-source RLHF implementation in the community. It integrates vLLM/SGLang as the rollout engine and Ray for distributed scheduling.

Design highlights:

  • Modular design: Actor, Critic, Reward, and Reference models are deployed independently
  • vLLM/SGLang integration: leverages the high-throughput characteristics of mature inference engines
  • Ray orchestration: flexibly assigns GPUs to different roles
  • Multiple algorithm support: PPO, DPO, GRPO, REINFORCE++

Typical deployment topology:

GPU utilization optimization: OpenRLHF maximizes GPU utilization through packing and async scheduling:

  • Rollout and training can overlap (near on-policy)
  • Reward and Reference computations can run in parallel
  • Dynamic batch size adapts to varying sequence lengths

9. Multi-turn RL

RL in the Agent Loop

Modern LLM agents require multi-turn interaction: calling tools, observing results, continuing to reason. This poses new challenges for RL systems.

Complexities of multi-turn rollouts:

  • Variable-length trajectories: different queries may require anywhere from 1 to 10+ tool calls
  • Asynchronous execution: tool call latency is unpredictable (API calls, code execution)
  • Credit assignment: how should the reward be distributed across turns?
  • Batching difficulties: different samples are at different stages, making naive batching impossible

10. Training-Inference Mismatch

On-Policy vs Off-Policy Trade-offs

In the ideal case, PPO is an on-policy algorithm — rollouts must be generated by the current policy. In distributed systems, however, strict on-policy training carries enormous overhead.

Truly On-Policy Near On-Policy (Importance Sampling)
Re-rollout before every update Rollout and training overlap
Data from the latest policy Data may come from an older (stale) policy
Training and inference must alternate Requires importance sampling correction
Low GPU utilization (mutual waiting) High GPU utilization
KL divergence is exact Staleness can introduce bias

Practical solutions:

IS clipping clip importance weights biased but variance-controlled
μ-PPO multi-step IS correction theoretically elegant but complex

Exercise 3: Designing a Weight Update Strategy

GPU topology: 2 nodes, each with 8 × H100 (80 GB); intra-node NVLink (900 GB/s), inter-node InfiniBand (400 Gb/s); model has 70B parameters (FP16 ≈ 140 GB); requirement: Training (FSDP) + Inference (TP=4) deployed simultaneously. Design the optimal GPU allocation and weight sync strategy.

Recommended approach:

Rationale:

  1. Training owns Node 0 exclusively: with 70B FSDP across 8 GPUs, each card holds 17.5 GB of parameters plus optimizer states (70 GB/card), which fits within H100’s 80 GB. Intra-node NVLink ensures efficient AllGather.
  2. Inference on Node 1: two TP=4 instances process different rollout batches in parallel, increasing throughput. TP=4 communication is bottleneck-free over NVLink.
  3. Weight Sync: use NCCL broadcast (cross-node over InfiniBand). 70B FP16 ≈ 140 GB takes ~2.8 s over 400 Gb/s IB. Combined with double-buffering, the transfer can happen asynchronously while the next rollout batch begins.
  4. Utilization optimization: training and inference overlap — while the training update runs, inference continues rollout with the old weights; once the update finishes, NCCL broadcast pushes the new weights. Bounded staleness = 1.
Exercise 4: Analyzing On-Policy vs Off-Policy Trade-offs

Training a 7B model with RLHF, we observe the following metrics at different staleness levels: IS weight variance, KL divergence, reward improvement, and GPU utilization.

Staleness IS Weight Variance KL Divergence Reward Improvement GPU Utilization
0 0 0.02 +0.15/step 35%
1 0.08 0.05 +0.13/step 55%
3 0.35 0.12 +0.10/step 75%
5 1.2 0.25 +0.05/step 85%
10 5.8 0.8 -0.02/step 92%

Analyze: (a) What is the optimal staleness? (b) Why does reward actually drop at staleness=10? (c) How can we mitigate the problem without reducing staleness?

(a) Optimal staleness analysis (wall-clock improvement ∝ reward_per_step × throughput; set base throughput = 1 at 35% util):

Optimal staleness = 3, striking the best balance between per-step efficiency and throughput.

(b) Why reward drops at staleness=10: IS weight variance = 5.8 means gradient estimates are extremely noisy; KL = 0.8 indicates the current policy has diverged significantly from the policy that generated the rollouts; this is equivalent to training on completely uncorrelated data — high variance causes the optimizer to “random-walk” rather than converge.

(c) Mitigation (without reducing staleness):

  • IS Clipping: clip importance weights to [0.5, 2.0], trading unbiasedness for stability
  • Reduce PPO epochs: drop from 4 to 1-2, reducing per-step policy drift
  • Increase KL penalty β: constrains the rate of policy change, reducing effective staleness
  • Early stopping: monitor approx KL; discard the batch when it exceeds a threshold
  • Partial refresh: use a mixed batch of 50% old data + 50% fresh rollouts

Exercise C: PPO vs GRPO Memory Comparison

Given a 70B parameter model for RL training. PPO maintains Actor + Critic + Reference + Reward (4 models); GRPO maintains Actor + Reference (2 models); Adam + BF16; each H100 has 80 GB.

(a) Total memory requirements: a trainable model (Adam BF16) costs ~16 bytes/param (2B weights + 2B gradients + 4B+4B Adam states); a frozen inference-only model costs 2 bytes/param.

(b) Minimum H100 count: PPO 2520/80 = 31.5 → at least 32 GPUs; GRPO 1260/80 = 15.75 → at least 16 GPUs.

(c) GRPO sampling overhead: group_size=16 means sampling 16 responses per prompt (PPO typically uses 1), i.e., 16× the inference volume. But this is pure inference (no backward pass) and can be handled efficiently with vLLM batching. Key insight: inference cost is far lower than training a full Critic model — cheap inference substitutes for expensive Critic training.

Exercise D: System Impact of On-Policy Training and Overlap

Online RL requires rollouts from the current policy (on-policy), creating a “training-inference pipeline bubble.” If rollout takes 60% of wall time and training takes 40%:

No overlap (sequential execution): training GPUs are idle during rollout → effective utilization is 40/(60+40) = 40%.

With overlap (disaggregated + pipeline): separate the training and inference clusters. The training cluster trains on batch N while the inference cluster simultaneously generates batch N+1 with (slightly stale) weights. Both clusters run at close to ~90-95% utilization (with only a small bubble during weight sync).

Exercise F: System-Level Detection of Reward Hacking

During GRPO training the model may “hack” the reward model (achieving high RM scores while actual quality degrades).

(a) Monitoring metrics:

  1. KL divergence trend: KL() — spikes sharply when hacking occurs
  2. Reward-KL correlation: in healthy training reward rises while KL stays flat; when hacking, reward rises but KL explodes
  3. Output diversity: unique n-gram ratio, distinct-N — hacking often causes output collapse
  4. Specific pattern detectors: repetition, format gaming (excessive bullets/markdown), abnormal length
  5. RM score vs ground truth: periodically sample human eval / LLM-as-judge to detect divergence
