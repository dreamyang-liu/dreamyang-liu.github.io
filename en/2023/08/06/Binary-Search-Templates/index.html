Binary Search Templates

2023-08-06
Binary Search Divide and Conquer

99% of binary search bugs come down to not thinking clearly about the loop invariant. Lock in a half-open interval [lo, hi) template and handle all four boundary cases — >=, >, <=, < — with the exact same code.

Intuition: Not “Finding an Element,” but “Making a Cut”

Textbooks frame binary search as “find a target in a sorted array,” which leads everyone to agonize over: < or <=? Should mid subtract 1? Is right initialized to n or n-1? — all of that is surface noise.

What binary search is actually doing is: given a monotone boolean predicate pred(i) (False for a prefix, True for a suffix), find the first position where it’s True. That’s all. “Find target” is just “find the first position ≥ target, then verify” as a special case.

Shift your perspective to the predicate and all the boundary confusion disappears. The trade-off is that you must maintain your loop invariant rigorously:

The answer always lies within [lo, hi). Everything to the left of lo is False; everything at or to the right of hi is True.

Why is off-by-one so common? Because in a closed-interval [lo, hi] template, whether you write hi = mid - 1 or hi = mid depends on whether mid has already been verified — easy to get wrong. The half-open interval [lo, hi) naturally makes hi mean “the unverified right end,” so hi = mid is always valid — mid hasn’t been verified yet and can’t be “excluded,” so it becomes the new unverified right end.

Click “Next Step” to watch lo and hi shrink each iteration. Note: hi always points to “a position known to be True (or the out-of-bounds sentinel n)”; when the loop ends, lo == hi is the answer.

One Template, Four Boundary Cases

Memorize this one snippet. All four boundary cases reduce to “construct the right pred“:

What you want pred(i) Return
First arr[i] >= x arr[i] >= x lo
First arr[i] > x arr[i] > x lo
Last arr[i] <= x arr[i] > x lo - 1
Last arr[i] < x arr[i] >= x lo - 1

The rule: for leftmost-satisfying, apply directly; for rightmost-satisfying, flip the predicate and subtract one. The “flip” works because satisfying elements in a sorted array form a contiguous block — the position just before the first non-satisfying element is the last satisfying one.

Why does this template never infinite-loop or go out of bounds? Three things guarantee it:

  1. mid = (lo + hi) // 2 floors, so mid < hi, meaning hi = mid strictly shrinks the interval.
  2. lo = mid + 1 obviously shrinks the interval.
  3. hi is initialized to n, not n - 1 — this allows returning n for “answer doesn’t exist,” eliminating a lot of edge-case checks. After returning, just verify with lo < n and arr[lo] == x.

Mnemonics / Common Pitfalls

  • First rule: before writing code, say out loud what pred(i) is and which direction is monotone. If you can’t articulate it, don’t start — it will be wrong.
  • Always write the half-open interval [lo, hi). The closed-interval template has an infinite-loop trap (lo = mid doesn’t shrink the interval); the half-open one doesn’t.
  • Initialize hi to n, not n - 1. Returning n for “answer doesn’t exist” is far cleaner than a -1 sentinel.
  • mid = (lo + hi) // 2 floors; pair it with hi = mid. Do not pair lo = mid with floor division — it infinite-loops. If you truly need to update the left end, switch to mid = (lo + hi + 1) // 2. Best advice: don’t write that variant at all.
  • Validate after returning lo. lower_bound finds “the first True position” — it doesn’t guarantee target is actually there. You might be out of bounds or off-value. Write lo < n and arr[lo] == x rather than reasoning about edge cases in your head.
  • Overflow: not an issue in Python; in C++/Java always write mid = lo + (hi - lo) // 2.
  • In rotated arrays, compare against nums[hi], not nums[lo]. Comparing with lo fails on a non-rotated array like [1,2,3] — nums[mid] >= nums[lo] is trivially true but the “cliff” is not to the right.
