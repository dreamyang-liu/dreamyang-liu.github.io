Intuition — Monotone Motion of Two Pointers

The reason a brute-force double loop wastes time is that the inner loop rescans from the start every iteration, retrying combinations that are already known to be wrong. Two pointers are different: every step is informed by what the previous step revealed, so we never backtrack.

Why can we get away with never backtracking? Because the problem has monotonicity:

  • Opposing pointers: the array is sorted → moving left always increases sum, moving right always decreases it.
  • Fast/slow pointers: the speed difference is constant → relative displacement grows monotonically over time; if they’re supposed to collide, they will.

💡 What is a loop invariant? (click for a refresher)

A loop invariant is a statement that remains true at the start of every iteration. It’s not code — it’s a promise about “where we are right now”; when the loop terminates, that promise directly becomes your answer.

Proving “the entire loop is correct” head-on is hard, but you only need to verify three small things, and that’s equivalent to proving the loop is correct no matter how many iterations it runs (it’s essentially mathematical induction):

  1. Initialization: Does the statement hold before the loop begins? (The base case of induction.)
  2. Maintenance: Assuming it holds at the start of some iteration, does it still hold after that iteration completes? (The inductive step.)
  3. Termination: When the loop stops, does the invariant plus the fact that “the loop has ended” directly yield the answer?

Applied to the container problem, the invariant is: “the globally optimal pair always lies within the current [left, right] window”:

  • Initialization: the window starts as the entire array, so the optimal pair is certainly in it.
  • Maintenance: each iteration only discards the short-side line, and the lemma guarantees every discarded pair doesn’t exceed the already-recorded value → the optimal pair is never discarded and remains in the shrunken window.
  • Termination: when left == right the window closes and the loop stops; the maximum recorded during the process is the answer.

With the invariant in hand, you never need to worry about “accidentally discarding the optimal pair in some step” — the maintenance clause has permanently closed off that possibility. This is exactly why two pointers can “never backtrack” with confidence: backtracking is unnecessary because everything discarded is genuinely useless.

How to find your own invariant: ask yourself “At the start of this iteration, what have I already accomplished? What do each of my variables represent right now?” For example, slow = “the next position to write a result” ⟹ invariant: “[0, slow) is already the finished answer.” A good invariant often simultaneously explains why a variable has its name and why it points where it does.

This is structurally identical to “discarding an entire column” above: there we discard a row/column of a sorted array; here we discard all pairs the short line can form.

Practice Problems

Why do opposing pointers require a sorted array? What if it's unsorted?

Sorted → monotonicity → every move definitively shrinks the search space. Without sorting, that guarantee breaks. Two fallbacks: a hash table ( time + space), or sort first then use opposing pointers ( time, extra space). Which trade-off the problem calls for depends on the constraints.

In Floyd's algorithm, after slow returns to head, why do two pointers moving at the same speed meet at the cycle entry?

Because . Walking steps from the meeting point = going around the cycle times and retreating = the cycle entry. Walking steps from head also reaches the entry. Same speed, same time — they must meet at the entry. That’s all the magic in Floyd’s phase two.

How do you modify in-place dedup to allow at most 2 duplicates?

Look one position further back in the comparison: nums[fast] != nums[slow - 1]. That is, slow checks “the value written two writes ago”; a new element is allowed to be written only if it differs from that.

To allow up to duplicates, compare against nums[slow - (k-1)]. The pattern generalizes.
