Sliding Window

2026-06-02
Sliding Window Two Pointers String

Two pointers l and r: r keeps expanding to the right; when the window becomes “invalid”, l shrinks from the right; once valid again, update the answer. Each pointer moves at most N steps, so crushes the brute-force enumeration.

Intuition — Monotonic Advancement of Two Pointers

Think of brute-force enumeration of all subarrays as a 2D grid with cells. Sliding window only walks one monotone path: r only ever increases, l only ever increases. Together the two pointers take at most steps, giving .

Why doesn’t l retreat? Because moving r one step to the right only makes the window “more invalid” (more elements, larger sum, more duplicates). An l that has already been moved right to restore validity has no reason to go left again — that would only make the window invalid again.

When Can You Use Sliding Window

Key criterion: monotonicity. You must have:

  • Window expands → condition moves in one direction (more invalid / more valid)
  • Window shrinks → condition moves in the opposite direction

For example, “subarray sum target”: adding elements only increases the sum, removing them only decreases it — the validity is monotone, sliding works. For “exactly K distinct characters”: expanding or shrinking can both break the “exactly K” condition, there is no monotonicity, so you can’t slide directly (convert to “at most K minus at most K-1”, see below).

Get this wrong and you’re stuck: when you see a problem, ask first — “does expanding the window push the condition in only one direction?” Yes → you can slide.

Two Templates — Longest Valid vs. Shortest Cover

Template A: Longest Valid Window (shrink while invalid)

Intuition: exiting the while loop means the window just became valid again — this is the largest valid window with right as the right endpoint, so record it.

Template B: Shortest Cover Window (record while valid)

Intuition: entering the while loop means the window is already valid; every step of shrinking is a valid window, so greedily record the shortest. Once l has shrunk to the point where going further would make it invalid, exit and wait for r to expand more.

Mapping to Problem Types

Problem characteristic Which template ans update position
Find longest X subarray A: longest valid outside while
Find shortest X subarray B: shortest cover inside while
Count how many X subarrays Variant of A: ans += right - left + 1 outside while

The third variant is a high-frequency trick: after exiting the while loop, [left..right] is the largest valid window ending at right, so there are exactly right - left + 1 valid subarrays ending at right.

Three Rules to Write It Right

  • Symmetric enter/exit: whatever operation right does entering the window, left must undo on exit. Don’t forget to del from Counter when it reaches zero, otherwise len(cnt) will be wrong.
  • left only moves inside while: moving left outside the while breaks the amortized analysis.
  • ans position = problem intent: outside while → longest / count; inside while → shortest.

Memory Aid

One sentence: r expands until invalid → l shrinks until valid.

Three-question checklist:

  1. Does expanding the window push the condition in one direction (monotone)? No → can’t slide directly (or convert).
  2. Looking for longest or shortest? Longest → shrink while invalid, update outside while; Shortest → record while valid, update inside while.
  3. Are enter/exit operations symmetric? Counter zeroed out → delete; sum added → subtract.

When you see “contiguous subarray/substring + longest/shortest/count”, reflexively write two pointers with a while loop. You won’t go wrong.

Exercises

Why does the left pointer only move right and never retreat? What complexity does this guarantee?

After r moves right, the window can only become “more invalid”. An l that has already been moved right to restore validity has no reason to go left again — that would only make the window invalid again. Each of the two pointers moves at most steps, for a total of . This is a classic example of amortized analysis: even though there are two loops (for + while), the total number of while iterations is bounded by the total displacement of l.

Why can't "exactly K distinct characters" be solved with a direct sliding window? How do you convert it?

With exactly K, expanding can jump to K+1 (invalid) and shrinking can jump to K-1 (also invalid) — neither direction has monotonicity, so the while loop can’t maintain a clean invariant.

Conversion: exactly K = at most K minus at most (K-1). “At most K” is monotone (the larger the window, the more likely it exceeds K), so standard sliding window applies.

In Template A, why must `ans` be updated outside the while loop?

Inside the while loop, the window is in the middle of “shrinking from invalid back to valid” — intermediate states are all invalid. Exiting the while loop guarantees that [left..right] is a valid window, and specifically the largest valid window with right as the right endpoint. Updating ans while invalid would corrupt the answer.
