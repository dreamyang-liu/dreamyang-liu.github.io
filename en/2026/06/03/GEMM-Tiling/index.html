GEMM Tiling: How Matrix Multiplication Maps to Tensor Cores

2026-06-03
gemm tiling tensor-core gpu triton mlsys

Matrix multiplication (GEMM) is the operator that consumes the vast majority of compute in deep learning. This post starts from a concrete C[64, 24576] = A[64, 8192] × B[8192, 24576], and walks through how it maps layer by layer onto the GPU’s Grid / Block / Warp / Tensor Core hierarchy — and why the Decode phase wastes compute. The main text is Markdown; key mechanisms have interactive animations.

1. The Big Picture: Why Tiling

The core idea is output-stationary tiling: partition the output into tiles, assign each tile to an independent thread block, and accumulate along the dimension in a loop.

2. Hierarchical Breakdown: From Grid to Tensor Core

Back to the real-scale GEMM, the GPU splits it across four levels. ② Block Level: Load SRAM + K Loop

Each Block is executed by 256 threads (= 8 Warps) on one SM. The 256 threads cooperate to move one tile (2 KB) and (4 KB) from HBM into SRAM (Shared Memory), shared across all 8 Warps. They then loop 512 times () along , with a step size of — the reason it is 16 is that the Tensor Core’s mma.K = 16.

③ Warp → Register → Tensor Core

Each Warp uses wmma::load_matrix_sync to load the SRAM tile into 16×16 fragments in registers, then feeds them to the Tensor Core via wmma::mma_sync. The result accumulates into a register-resident accumulator , which never leaves the registers.

One MMA instruction on a Tensor Core computes , i.e., FLOPs in just 1–2 cycles. Physically this is a 4×4 FMA array × 4 TCs, internally split into 64 sub-operations, but the ISA wraps it as 16×16 — transparent to the programmer. Inputs are FP16; accumulation is FP32.

3. Memory Hierarchy: HBM Is the Sole Bottleneck

Data flows HBM → SRAM → Register → Tensor Core — each level is faster and smaller:

Level Capacity Bandwidth What it holds
HBM 80 GB 3.35 TB/s All weights (e.g., 384 MB)
SRAM (Shared Memory) 228 KB/SM ~30 TB/s A_tile + B_tile
Register 256 KB/SM ~60 TB/s 16×16 fragments
Tensor Core — 989 TFLOPS 8192 FLOPs/instruction

Arithmetic Intensity determines where the bottleneck is:

In other words, for every byte read from HBM you need to perform at least 295 floating-point operations to keep the Tensor Core fed.

Bottleneck: HBM → SRAM. The GEMV in the Decode phase has an arithmetic intensity of only ~1 FLOP/Byte, far below 295, so the Tensor Core spends 99% of its time waiting for data.

Solution: increase batch size. With batch=1, weights are read once and used once; with batch=64, each read is reused 64 times, lifting TC utilization from ~6% to near 100%.

4. Why Decode Is Slow: the Fragment Padding Problem

The minimum granularity of a Tensor Core is 16×16. When , the missing rows are zero-padded. The hardware still executes all 8192 FLOPs — most of them are wasted work.

Scenario Effective rows Efficiency
Decode: batch=1 1 / 16 rows have data ~6%
Prefill: batch=64 16 / 16 rows all have data 100%

With batch=1, 15/16 fragment rows are zeros; ~94% of TC work is wasted. Increasing batch fills those 16 rows, making every FLOP count.

The essence of Continuous Batching: pack enough requests to fill all 16 rows of a fragment — this is exactly why LLM serving concatenates tokens from multiple requests into one large GEMM, converting memory-bound Decode into compute-bound efficient computation.

5. Summary

  • Tiling cuts a matrix that is too large for on-chip storage into tiles that fit. The output-stationary scheme keeps the accumulator in registers throughout, writing back only once.
  • The GPU decomposes GEMM across four levels: Grid (partition output space) → Block (slice K, load SRAM) → Warp (issue MMA instructions) → Tensor Core (16×16×16).
  • Data flows HBM → SRAM → Register → TC; HBM bandwidth is the sole bottleneck, with a machine balance point of ~295 FLOP/Byte.
  • Increasing batch size raises both data reuse and fragment fill rate — the key to pulling Decode from memory-bound back to compute-bound, and the core motivation for Continuous Batching.
