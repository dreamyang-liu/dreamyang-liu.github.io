Greedy Algorithms

2026-06-02
Greedy

At each step, pick whatever looks locally optimal and hope it leads to a global optimum. The hard part isn’t writing the code — it’s proving that the greedy choice is actually correct.

Greedy code is usually short, but correctness proof is the soul. Problems that look greedy are half the time actually DP.

Intuition — Conditions for Local Optimum → Global Optimum

Greedy works only when two hidden prerequisites are both satisfied:

  1. Greedy-choice property: The locally optimal choice at this step won’t ruin the globally optimal solution downstream.
  2. Optimal substructure: After making this step, the remaining subproblem is independent and can itself be solved greedily.

The moment any “locally optimal” choice constrains future options, greedy will break down and you must fall back to DP. A quick rule of thumb: can you construct a counterexample? If you can’t think of one in a minute, greedy probably works; if you find one, switch to DP immediately.

Three Classic Patterns

90% of greedy problems fall into one of the three patterns below. Recognize the pattern, apply the template.

1. Interval Scheduling — Sort by End Time

Form: Given a collection of intervals/tasks, find the maximum number of non-overlapping ones you can select/complete.

Key intuition: An interval that ends earlier leaves the most “room” for future intervals, so always greedily picking the earliest-ending one never hurts. The proof uses “greedy stays ahead” — by induction, after selecting k intervals, the greedy solution’s last end time is no later than that of any optimal solution.

Variants: sort by start time (merge intervals), sort by right endpoint (minimum arrows to burst balloons), sort by left endpoint (merge/insert). Default: think right endpoint first.

2. Regret-Based Greedy — Use a Heap to Undo Previous Decisions

Form: Maximize count or value subject to a budget/capacity constraint.

Key intuition: Greedily pack everything in without thinking; once the budget is exceeded, kick out the “most expensive” item — the heap top. The ejected item is always ≥ the current one, so the total cost is non-increasing while the count is preserved.

Classic problems: Course Schedule III, Minimum Number of Refueling Stops, IPO. Recognition signal: deadline/capacity constraint + maximize count.

3. Exchange Argument — Correctness of Sorting via “Swapping Adjacent Elements Doesn’t Make It Worse”

Form: Find an ordering of a set of objects that optimizes some metric (e.g., total completion time, lexicographic order, minimum penalty).

Key intuition: Assume the optimal solution has two adjacent elements in a different relative order than your sorting. Prove that swapping them doesn’t make the answer worse. By bubble-sorting all “greedy-violating” pairs, you still get an optimal solution — so the greedy ordering is correct.

Typical problems: merging fruits (smallest first), queen game (sort by ), Huffman coding.

Memory Aids / Common Pitfalls

One-liner for the three patterns: sort by right endpoint (intervals) / max-heap regret (capacity) / pairwise swap (ordering).

The three most common traps:

  1. Looks greedy, actually DP: The classic counterexample is the 0/1 knapsack — greedy by value/weight ratio doesn’t work, you need DP. Test: are subproblems independent? In a knapsack the remaining capacity changes with each choice → not independent → DP.
  2. Wrong sort key: Sorting by left endpoint is often wrong in interval problems; default to right endpoint. Watch for overflow in ratio-sort problems (e.g., IPO).
  3. Forgetting to maintain total in regret greedy: Every push/pop must be accompanied by a synchronized update to the resource used, otherwise the next iteration’s check will be wrong.

Not sure if greedy applies? Three questions: (1) Is there a counterexample? (2) Are subproblems independent? (3) Can you write an exchange argument or a stays-ahead proof? All three pass → go ahead and be greedy; any one blocks you → write DP instead.

Exercises

When should you use "exchange argument" vs. "greedy stays ahead" as a proof technique?

Exchange argument suits “permutation/ordering” problems — proving that a certain ordering is optimal (sort by deadline, by ratio, by ). Greedy stays ahead suits “selection” problems — picking one element per step and proving your set is never worse than the optimal at each step (interval scheduling, minimum spanning tree).

Why does regret-based greedy use a max-heap? What goes wrong with a min-heap?

When regretting, you eject the element with the highest cost so far, which frees up the most budget and drops the total cost the most. Using a min-heap means ejecting the cheapest element — you might still be over budget, and you’ve thrown away a “cheap choice” for nothing. The max-heap maximizes the marginal gain of each regret step.

Why can't you solve the 0/1 knapsack greedily?

Counterexample for greedy by value/weight: capacity 50, items (60,10), (100,20), (120,30) with ratios 6/5/4. Greedy picks the first two for a total of 160, but the optimal is the last two for 220. Reason: picking an item changes the remaining capacity, making subproblems non-independent — there is no “greedy-choice property”. This case requires DP to enumerate all states.
